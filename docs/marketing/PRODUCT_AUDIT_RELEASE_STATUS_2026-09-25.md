## Реализовано в кандидате

- Историческая гибридная FIFO-себестоимость присутствует в родительском релизе `54c1765`.
- Общие расходы магазина, месячные регулярные шаблоны и безопасный CSV-импорт добавлены в `1433e97`. Предпросмотр показывает ошибки и дубли; до подтверждения импорт не пишет данные. Импортированные расходы не влияют на P&L до явного включения.
- Версионные многокомпонентные BOM и производственные выпуски учитывают вариант WB (`chrt_id`); вариант проходит до движений, себестоимости, готовых FIFO-слоёв, закупок, продаж и возвратов. Для варианта разрешён только точный BOM или явно общий BOM `chrt_id=0`.
- НЗП доступно в React: вариант проходит через выдачу сырья, выпуск заготовок, FIFO-упаковку и готовый слой. Старые партии сохраняются как `0/0`; их можно использовать только для проверенного базового товара с каталогом `sizes: []`. Партии разных вариантов не смешиваются. Закрытие смены проверяет каталог до выбора BOM и не создаёт проводки для неизвестного `chrt_id`.
- Вложенное НЗП по полуфабрикатам реализовано в UI и API: версионный BOM может потреблять готовые полуфабрикаты, каждый выпуск получает отдельный готовый FIFO-слой, а списание использует фактическую себестоимость потреблённых партий. Полный маршрут сохраняет защиту от повторной проводки и отмены уже использованных партий.
- Происхождение вложенных FIFO-слоёв видно в производственном журнале: закреплённая версия BOM сопоставляется с фактической версией выпуска-поставщика; расхождение не меняет законное FIFO-списание и показывается явно. Для старых производственных партий без однозначной связи, начального и внешнего остатка показываются разные статусы неизвестного происхождения. Повторный идемпотентный POST возвращает тот же provenance, что первоначальный ответ и журнал.
- Календарь производственной мощности подключён к React, единицы материалов отображаются из справочника (`м`, `кг`, `л`, `шт`).
- Планирование потребности в сырье работает как явный read-only предпросмотр по открытым производственным заданиям, версионному BOM, физическому и FIFO-остатку, открытым закупкам, единицам/рулонам и срокам поставщика. Подтверждение требует активного поставщика и создаёт только внутреннюю заявку со статусом `Запланировано`; поставщику ничего не отправляется. Повтор с тем же ключом идемпотентен, а изменение исходных данных делает предпросмотр устаревшим.
- В follow-up проверках исправлено сохранение traceability всех вариантов при объединении идентичного BOM. Добавлены тесты multi-SKU aggregation, BOM version/fallback, перераспределения с превышением, разных единиц, статусов/ETA открытых заказов, отменённого остатка, ошибочного статуса, rollback при сбое второй заявки поставщику, UI blocker matrix и HTTP wrapper-контракта.
- Исправлены публичные формулировки калькулятора (внешние расходы вводятся вручную, импорта нет), руководства о данных WB API и слова «финансовый учёт» на главной. Старые внутренние outreach/article черновики помечены как архивные, содержат фактологические исправления и не отправлялись/не публиковались.

- Доступ к кабинету Директа/аналитики в текущей сессии не подтверждён. Фактическая модерация, конечные URL, активность кампаний и конверсии требуют проверки в авторизованном кабинете.
- Повторная read-only проверка 25.09: `https://marketshelper.ru/` — 200, `https://marketshelper.ru/sitemap.xml` — 200, `https://www.marketshelper.ru/` — 404. Кандидат содержит отдельный HTTPS-router с постоянным редиректом на apex и сохранением path/query; правило заработает после безопасного выпуска gateway-конфигурации.
- SSH alias `marketshelper-staging` фактически ведёт на production-хост. Read-only инвентаризация подтвердила здоровые gateway, tenant, provisioner и Traefik. На production provisioner отсутствует `WB_SAAS_BACKUP_ENCRYPTION_KEY`; локальный provisioner также без этого ключа. Это отдельный ключ для архивов backup, не tenant-ключ `WB_SAAS_DATA_ENCRYPTION_KEY`: deploy helper получает tenant encryption env из gateway, но backup fail-closed без собственного ключа. Deploy helper не имеет dry-run: он создаёт проверенный backup, затем останавливает и заменяет tenant. Не запускать его без ключа. Не генерировать и не менять ключ. Перед выкладкой нужны существующий секрет в серверном secret store, зашифрованный control-plane backup и доказательство восстановления согласованной SQLite-копии.

## Граница результата

Кандидат собран и проверен локально, но production tenant/gateway не менялись. Для выкладки требуется настроенный владельцем существующий `WB_SAAS_BACKUP_ENCRYPTION_KEY` на provisioner (не `WB_SAAS_DATA_ENCRYPTION_KEY` tenant), зашифрованный и проверенный backup/restore, проверка целостности базы, rollback и production health/business probes. Секрет не запрашивать в чате, не генерировать и не заменять. A-запись www уже указывает на тот же хост и TLS-сертификат действителен, но редирект заработает только после безопасного обновления gateway. Локальные тесты и smoke не заменяют эти проверки.
