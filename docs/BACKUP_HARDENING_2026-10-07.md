# Backup hardening acceptance

Implemented source changes, not proof of installed cron or delivered notifications:

- Every tar helper uses UID/GID10001. A restricted root initialization helper creates only a validated backup namespace and assigns it to10001 with mode0700; called during tenant creation and before backup. It has CHOWN/FOWNER, no network and a15-second wait. Archive helpers have no capabilities, read-only source volumes and a240-second wait; failures remove the helper and incomplete files.
- Plain temporary archives are created0600; encrypted files and restored temporary outputs are created0600 before any bytes are written and atomically published. Crypto streams1MiB chunks and has a120-second progress deadline. Stale incomplete files older than one hour are removed before the next backup in their namespace.
- The backup HTTP client allows600seconds, exceeding initialization15 + archive240 + encryption120. Pre-release application ZIP backup runs as10001 and retains five archives. Existing root-owned ZIP files may require an operator ownership repair; they are not removed arbitrarily.
- `scripts/backup_offsite.py` uses rclone copy/check and only `**/*.tar.gz.enc`; partial files and legacy plaintext archives cannot be copied. It never uses sync. Remote deletion is disabled unless both an explicit7..3650-day policy and `WB_SAAS_OFFSITE_DELETE_CONFIRMED=1` are provided. `-v --log-file` writes to a0600 log.
- `scripts/backup_offsite.py --check` is an independent hourly freshness watchdog. It checks every required local group and the last verified offsite copy against26hours, writes separate health evidence and invokes an optional configured alert command. Local backup orchestration also invokes that command on failure. Hook success means accepted handoff, not recipient delivery.
- `scripts/backup_alert.py --to <owner email>` runs inside the gateway, receives allowlisted event codes through bounded stdin and uses configured SMTP. Missing SMTP, rejected event or failed transport exits nonzero; private provider output is never placed in the alert body.

Host integration requirements (root owns deployment):

1. Configure `WB_SAAS_BACKUP_REQUIRED_GROUPS=control-plane,demo,mvvorokov,marketing`, `WB_SAAS_OFFSITE_REMOTE=timeweb-s3:marketshelper-backups` and a status/log path outside copied files. Replace existing rclone sync cron with the script; install a separate hourly `--check` job so a stopped daily cron still alerts.
2. Configure `WB_SAAS_BACKUP_ALERT_COMMAND_JSON` as the JSON argv for `docker exec -i <gateway> python /app/scripts/backup_alert.py --to <owner email>`; ensure the helper is present in the committed gateway image. No real message was sent by tests.
3. Configure `WB_SAAS_OFFSITE_PUBLIC_RECIPIENT` with an RSA3072 (or larger) public PEM; the private PEM is retained only by the owner outside the server and Git with restrictive ACL. `backup_offsite_envelope.py` wraps each existing encrypted archive in a fresh AES256-GCM envelope; the AES key is wrapped with RSA-OAEP-SHA256. The authenticated header includes recipient identity, exact source hash and length. The server never requires the private key. `WB_SAAS_OFFSITE_STAGING_DIR` must be outside the original backup root; budget one additional encrypted copy of retained archives. Only the freshly validated envelope file list is passed to rclone; plaintext/stale staging leftovers cannot be uploaded. Copies target the separate `/offsite-v2` namespace and content/recipient hash filenames; previous remote originals remain untouched. A missing public recipient stops the new v2 upload and reports an error; install the new cron only after a successful owner-side decrypt rehearsal. Owner attestation `WB_SAAS_OFFSITE_KEY_ESCROW_CONFIRMED=1` confirms separately retained recovery key but does not replace a restore test.
4. `provisioner.app.migrate_legacy_backups(group,keep_days,remove_expired=False)` creates an encrypted replacement, decrypts it to a private temporary file and compares exact streaming SHA256 before any deletion. Only `remove_expired=True` plus an expired explicit retention period permits removal of the original; failure retains plaintext and removes a newly failed replacement. This is an operator migration, not part of the timed nightly archive job. Root must inspect actual legacy presence and run the explicit policy if required. Originals are excluded from new offsite copies.

Verification: small real AES-GCM encrypted round-trip/authentication-failure tests; private creation/collision/timeout cleanup tests; fresh namespace/helper policy mocks; logical2GiB stream regression consuming2048 bounded chunks with a fake cipher (not a real2GiB runtime throughput measurement). Real largest-volume backup latency and offsite restore still require host acceptance.

Offsite recovery: run `python scripts/backup_offsite_envelope.py decrypt <downloaded-v2-envelope> <original-backup.enc> --private-key <owner-local-private.pem>` locally. Then restore the resulting original AES-GCM backup through the existing procedure with the separately escrowed original backup encryption key. Losing either recovery secret prevents restore; neither private key nor original backup key belongs in Git or an alert. Envelope tests cover real RSA3072/AES256-GCM streaming roundtrip, wrong recipient, tampering, truncation, source mutation, atomic0600 output, cache corruption and plaintext staging exclusion. No production keys or cloud operations were performed by the agent.

Primary rclone contract: [explicit file lists](https://rclone.org/filtering/#files-from-read-list-of-source-file-names) ignore other filters and silently skip missing entries; the helper therefore validates the list and rechecks local ciphertext hashes after upload verification. [rclone check](https://rclone.org/commands/rclone_check/) runs with `--one-way --download` to compare ciphertext contents without assuming a remote checksum is available. No `sync` or delete-excluded behavior is used. Staging uses one cached encrypted copy per source/recipient; root must budget retained-archive capacity and configure a separate safe cache-retention policy rather than blindly pruning originals or remote backups.
