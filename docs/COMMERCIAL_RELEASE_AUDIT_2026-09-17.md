## Блокеры до полноценного коммерческого релиза

### P0. Частично сломан контур «Качество магазина» WB

Боевой `GET /api/v1/dashboard/customer-quality` после `release-20260917-audit18` больше не падает и больше не возвращает ошибку по карантину: клиент повторяет запрос с обязательным `limit=1000`. Сейчас для конкретного токена остаются две внешние ошибки:

1. `rating`: WB 403 — токен не удовлетворяет дополнительным требованиям категории Feedbacks and Questions.
2. `return_history`: WB 404 — раздел временно не отдаётся этому кабинету.

Интерфейс показывает безопасное уведомление о частичном покрытии вместо подстановки результата как полного. Рейтинг требует сервисный токен категории «Отзывы/Вопросы», а возвраты — доступ к аналитике; это проверяется настройками WB, а не исправляется повтором запроса. Для полного коммерческого покрытия нужно добавить проверку этих категорий при подключении токена и оставить явный статус недоступного раздела.

### P1. Раздел «Поставки» не использует уже полученные данные WB

Backend получает `wb_new_orders` и `acceptance_coefficients`, но frontend их отбрасывает. Окна приёмки на экране заданы текстом «нет»/«нет данных» и не зависят от ответа WB. Также в редизайне нет действий FBS по карточке поставки: подробности, состав, QR-код/стикеры, сборочные заказы и передача поставки.

Нужно вывести реальные коэффициенты и новые FBS-заказы, добавить состояния «нет доступа/нет данных» и подключить рабочие операции поставки.

### P1. Не закрыт полный операционный охват WB API

В `tenant-app/wb_api.py` нет рабочего контура для управления статусами и метаданными FBS-заказов, создания/передачи поставок, DBW/DBS/самовывоза, управления кампаниями и промокалендарём, редактирования карточек и медиа, складов продавца, истории остатков и расширенной воронки. Эти категории есть в официальном каталоге WB API, но текущий редизайн их не предоставляет.

Для платного продукта нужно либо реализовать приоритетные операции, либо явно ограничить тариф и интерфейс только поддержанными возможностями.

### P1. Рабочее расписание в текущем tenant выключено

В production есть определение отчёта, но оно сейчас `enabled=0`, `email_enabled=0`, `telegram_enabled=0`. Это не дефект очереди: расписание сохранено на паузе и без доставки. Перед коммерческим использованием tenant должен включить нужное расписание и выбрать каналы; для нового tenant нужен понятный onboarding без скрытого выключенного состояния.

## Ограничения проверки

- Нативные iOS/Android приложения не собраны и не опубликованы; проверены браузерная мобильная версия и PWA.
- Чистый checkout не воспроизводился: рабочая папка содержит ранее сделанные изменения.
- Полный `pip-audit -r requirements.txt` на Windows блокируется пакетом `uvloop`, который не собирается на Windows. Lock-файлы проверены отдельно через `--no-deps --disable-pip`.
- Реальные изменения цен, рекламных ставок и боевые ответы покупателям не выполнялись.

## Решение по готовности

Кодовый пакет годен для контролируемого paid pilot: сборка, тесты, Docker и текущий tenant проходят. Полный коммерческий релиз для новых клиентов пока не закрыт из-за P0 по customer-quality и P1-разрывов в поставках/WB API. Следующий релизный срез должен сначала устранить P0, затем подключить реальные данные поставок и провести ручную приёмку на физическом телефоне.

Официальный каталог категорий WB API: https://dev.wildberries.ru/docs/openapi/api-information .
