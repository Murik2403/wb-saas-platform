# Таймауты финансов за 90 дней — 12 октября 2026

На боевом mvvorokov браузер прерывал `/dashboard/finance` и `/dashboard/management-pnl/monthly` через 20 секунд. За ошибкой помесячного отчёта оставалась таблица прежнего периода; её даты и CSV не подтверждали результат нового запроса.

## Диагностика

Один подписанный read-only запрос finance90d внутри live контейнера завершился HTTP200 за **15.485 с**. До диагностики все пять tenants имели нулевые OOM/restart counters; нехватка RAM не подтверждена. Последний tenant release `3933d2d` не менял backend относительно `32f67d7`.

На отдельном контейнере с SQLite online snapshot реальных данных (327 MB), отключённой сетью и заданиями, cProfile показал:

- dashboard90d: 19.857 с; historical COGS projection 8.806 с, FIFO read/reconciliation 5.674 с;
- monthly90d: 17.748 с; четыре COGS projection 9.317 с, четыре FIFO reconciliation 5.102 с;
- около 36 000 Pandas Series создавались через iterrows. Итоговый dashboard занимает около 48 KB; гипотеза отказа кэша из-за лимита 32 MiB не подтвердилась.

Важен полный поток страницы: несколько расчётов стоят в общей очереди защиты памяти. Дополнительное вычисление в очереди увеличивает время запросов с индивидуальным лимитом 20 секунд. Синхронных WB balance retry в этом пути уже нет.

## Исправление

- COGS projection использует tuple/scalar iteration с заранее определёнными колонками и счётчиками ID. Сохранены проверки дубликатов, знаков возврата, отсутствующей себестоимости и ручных источников.
- Dashboard сохраняет только компактную FIFO-сводку из уже прочитанных строк; finance использует её вместо второй сверки того же окна. Для старых/injected snapshots оставлен fallback.
- Помесячный WB результат кэшируется по разрешённому интервалу; write/sync очищает общий кэш. Налоги добавляются на независимую копию, настройки и ответы не загрязняют базовый результат.
- Две P&L панели очищают данные при смене периода/ошибке и игнорируют поздние ответы отменённых запросов. Старый CSV и статус готовности при ошибке скрыты.

Клиентские таймауты и число одновременно работающих тяжёлых handler не увеличиваются. Числовые формулы не меняются.

## Проверка перед коммитом

602 frontend tests с двумя workers, tsc-b; 661 tenant-api tests; 1092 tenant-app tests, 1 skipped, 37 subtests. Предварительные red regressions воспроизводят iterrows, повтор FIFO, отсутствие monthly cache и старый период в UI.

Фиксированная синтетика 15 000 строк: projection 0.907 → 0.125 с; подробные строки/SKU/store и финансовый/monthly результат совпадают со старым кодом. Это дополнительная проверка, не замена приёмки на реальном snapshot.

## Особенности операторских проверок

Первая попытка остановилась до tenant swap: helper передавал demo глобальный namespaced keyring вместо scoped tenant keyring. После корректного выбора пространства ключей все архивы проверены без замены существующих ключей. Retention в helper увеличивается относительно текущего количества; история архивов не сокращается.

Первая замена demo была автоматически отменена из-за переходного внешнего HTTP404 до появления healthy route. Прежний ID восстановлен, повторная проверка добавила ограниченное ожидание 404/502/503 до 45 с; на повторной выкладке все внешние health прошли. Отдельный финальный pin возобновлён после исправления подстановки имени env во вложенном crypto gate; повторной замены tenant-контейнеров при pin не было.

Оговорка диагностики backup: промежуточный whole-file digest ошибочно превысил память отдельного exec процесса provisioner. Основной сервис сохранил health без перезапуска; это событие возникло после первоначальной фиксации нулевых counters и не объясняет пользовательский таймаут. Helper исправлен на streaming digest, окончательный encryption/decryption/integrity gate прошёл; production backup-код этой правкой не меняется. Существующие задачи Claude по согласованным backup-снимкам сохраняются.
