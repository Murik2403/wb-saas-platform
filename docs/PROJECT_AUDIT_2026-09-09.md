## Оставшиеся задачи по порядку

### P1 — изоляция внутренних запросов клиентов

`gateway/provisioning.py` передаёт всем клиентским контейнерам один `INTERNAL_API_SECRET`. В `gateway/internal_routes.py` секрет проверяется независимо от переданного `slug`. Компрометация одного контейнера даёт возможность обращаться к внутренним операциям от имени другого slug, включая создание Telegram link-code и доставку отчётов.

Следующее исправление: отдельные клиентские credentials, привязанные к slug, проверка на gateway и миграция уже созданных контейнеров. Нужен тест «ключ A + slug B → 403». Простая замена проверки без миграции сломает существующую доставку; текущие ключи не менялись.

### P1 — восстановление резервной копии при работающих процессах

`tenant-app/backup_tools.py:restore_backup` удаляет WAL/SHM и заменяет файл базы через `os.replace`, не останавливая читателей/писателей. На Windows открытый файл может блокировать замену; на Linux старые соединения могут оставаться на старом файле. Наличие safety backup не обеспечивает согласованность работающих процессов.

Следующее исправление: режим обслуживания с остановкой всех писателей, проверка архива и settings до изменения состояния, проверенное восстановление и запуск заново. Регрессионные сценарии — открытое WAL-соединение, повреждённый архив, невалидный settings, ошибка на этапе замены. Живая база не восстанавливалась.

### P1 — защита изменяющих запросов нового API

Новый API опирается на loopback локально и ForwardAuth в контейнере. Собственной проверки Origin/CSRF у изменяющих маршрутов нет; CORS не является запретом выполнения простого POST, например запуска синхронизации без тела.

Следующее исправление: проверка Origin/CSRF для браузерных операций с учётом Vite proxy и production host, тесты внешнего Origin, корректного Origin и серверных вызовов. Прямой API не следует публиковать в обход gateway.

### P2 — локальные интервалы не означают работающий планировщик

`start-local.ps1` запускает только API и Vite. В отличие от контейнерного entrypoint, не запускает `sync.py --loop`, `agent_sync.py --loop`, `report_scheduler.py --loop`. Настройки интервалов сохраняются, но в таком режиме задачи сами не выполняются. Автобэкап вызывается в Streamlit `app.py`, а новый API его не вызывает — история бэкапов остаётся старой.

Следующее исправление: явный управляемый локальный supervisor и показ состояния задач в UI; ежедневный бэкап должен быть отдельной проверяемой задачей. Запуск внешних агентских действий должен оставаться отдельным управляемым поведением.

### P2 — рекламная статистика и свежесть по разделам

Последняя синхронизация #22 — partial. На предыдущем этапе отдельный запрос рекламы также получал HTTP 500 от WB; в этой серии повторный импорт не запускался. Ошибка корректно не стирает старую рекламу. Нужны дата успешной загрузки каждого раздела и отдельный повтор рекламы, чтобы не гонять весь импорт.

### P2 — неполная себестоимость

В реальной базе `costs` содержит 0 строк. Предупреждение интерфейса об отсутствии затрат обосновано. Нельзя считать показанную маржу подтверждённой прибылью, пока пользователь не внесёт себестоимость. Нужна также проверка частичного покрытия ассортимента: наличие одной заполненной строки ещё не означает полноту затрат.

### P2 — воспроизводимость и эксплуатация

В проекте существуют Streamlit, Next и Vite, два API с одинаковым именем модуля, старый bridge. Перенесённые .venv уже потребовали восстановления. Скрипты запуска считают любой занятый нужный порт подходящим сервисом. Следует закрепить основной поддерживаемый путь, проверять identity/health сервиса и вынести зависимости разработки в отдельный файл/lock. Python-зависимости преимущественно диапазонные, результат новой установки не полностью воспроизводим.

### P3 — производительность и поддерживаемость

Холодные dashboard-запросы занимают около 1.1–1.3 секунды на этой базе; data-quality — 1.6 секунды. Расчёты через большие DataFrame сериализованы общим build-lock. Нужны профилирование и выборочные SQL-агрегации, прежде чем повышать нагрузку. Большие `App.tsx`, `data-source.ts` и API усложняют согласованность контрактов. FastAPI выдаёт предупреждение об устаревшем startup on_event; Next ESLint — три неиспользуемых типа.
