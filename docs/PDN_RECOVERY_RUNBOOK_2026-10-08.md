# Восстановление после удаления аккаунтов

Независимый реестр находится вне тома gateway_data: `/opt/wb-saas/erasure-ledger/erasures.sqlite3`, в контейнере `/app/erasure-ledger/erasures.sqlite3`. Каталог принадлежит UID/GID10001, режим0700; файл0600. Записи содержат хеш исходного id+created_at и время намерения удаления. Это блокировка восстановления доступа, не акт уничтожения архивов.

## Обязательные условия

- `WB_SAAS_ERASURE_LEDGER_REQUIRED=1` и `WB_SAAS_ERASURE_LEDGER_PATH=/app/erasure-ledger/erasures.sqlite3`.
- Использовать образ с erasure_ledger, erasure_recovery и проверкой в entrypoint. Старые rollback-образы без проверки запускать запрещено; сохранённый legacy-контейнер не является разрешённым вариантом восстановления.
- Не восстанавливать реестр вместе со старой базой gateway. Не создавать новый пустой реестр вместо потерянного. Потеря/повреждение реестра блокирует запуск до восстановления актуального независимого экземпляра.
- До открытия HTTP и запуска Telegram выполнить `python -m logic.erasure_recovery --check`. Entrypoint и ASGI lifespan делают это автоматически; обход entrypoint не отменяет проверку lifespan.
- Offline `--database` принимает существующий абсолютный путь SQLite и запрещён при PostgreSQL backend. Работать только с остановленной восстанавливаемой базой.

## Приёмка

В изолированной базе создать тестовый аккаунт, сохранить снимок, запросить удаление, восстановить старый снимок. Вход, обычная сессия, платежи, Telegram и выдача делегации должны быть заблокированы. Отсутствие реестра должно остановить запуск. Новый аккаунт с тем же id и другим created_at не блокируется ошибочно. Проверять без реальных удалений и рассылок.

## Завершение ранее запрошенного удаления

После сбоя удаления прежняя действующая сессия допускается только в `/account/delete` с повторной проверкой пароля, CSRF и подтверждения. После перезапуска восстановленные сессии удаляются; оператор может явно выполнить:

```sh
docker exec wb-saas-gateway-1 python -m logic.erasure_recovery --resume-deletion ACCOUNT_ID
```

Это команда удаления, не диагностическая проверка. Она допустима только для уже запрошенного удаления: незавершённые платежи блокируют операцию, новый аккаунт команда не удаляет. Архивы она не уничтожает. В приёмке на production эта команда не выполнялась.

## Оставшиеся ограничения

Реестр не доказывает физического уничтожения исторических копий, свободных страниц SQLite/WAL и офсайт-архивов. Записи об удалениях, совершённых до появления lifecycle-маркеров и уже отсутствующих в текущей базе, автоматически восстановить невозможно. Для полной аварии сервера требуется отдельная актуальная защищённая копия реестра; до её получения отсутствующий реестр должен оставаться блокирующим условием. Возраст архивов, манифест уничтожения и акты по приказу179 оформляются отдельно. Финансовые связи сохраняются по соответствующему основанию и не называются необратимым обезличиванием.
