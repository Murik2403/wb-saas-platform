# Полное восстановление и плотность кабинетов — отдельный стенд, 13 октября 2026

Запрос владельца: продолжить две приёмки отдельно от production; Claude занимается уроками. В этом этапе production не подключался по SSH/API, не менялся и не нагружался. Существующие локальные контейнеры, Docker Desktop/WSL-конфигурация и медиа уроков не изменялись.

## Границы приёмки

Полный DR требует свежих независимо доступных архивов control plane и пяти кабинетов, текущего независимого журнала удалений, сохранённых ключей и конфигурации deployment/TLS/host jobs; затем запуска на новом сервере и перезагрузки именно этого сервера. Создание пустой тестовой БД и перезапуск вложенного Docker не заменяют эту проверку.

Нагрузочная приёмка требует фактически завершённых ступеней 20, 25 и 30 со штатным API, nginx и постоянно работающим worker, одновременными расчётами и генерацией отчётов. Отказ admission, пропущенная фаза, пустой результат или недостаточная память считаются отказом/невыполненной проверкой. Настоящая WB/Ozon-синхронизация не проверяется без разрешённых внешних данных; её отсутствие не обозначается успешной синхронизацией.

Локально собраны новые gateway, provisioner и tenant; immutable IDs, OCI revision и SHA архива сохранены в `deliveries/full-recovery-density-20261013/image-proof.json`. Эти образы не выкладывались на production.
- Для механического запуска подготовлен отдельный Docker daemon внутри собственного контейнера: network=none, без host Docker socket, опубликованных портов и host bind, лимит 3 GiB / 4 CPU. Внутри настоящие образы gateway/provisioner/Traefik/proxies и одна синтетическая учётная запись. Внешние провайдеры отключены; test domain `.invalid`, локальный сертификат не является production TLS.
- У оператора есть проверки exact ID/label/image revision, внешнее наблюдение за памятью/диском/deadline, bounded restart и очистка только своих объектов. При отказе сохраняется диагностика класса/этапа/HTTP-статуса без URL токенов, текстов ошибок, env, тел и заголовков. Проверяется сохранность ID/образов/mounts посторонних контейнеров.
- Исправлена подготовка пустого synthetic gateway volume: до штатного startup guard явно создаётся тестовая схема. Для реального DR вместо этого требуется восстановленная БД; защита от воскрешения удалённых аккаунтов не ослаблялась.
- Разделены готовность прямого gateway health и готовность HTTPS-маршрута Traefik. В реальном локальном attempt3 первые запросы маршрута вернули 404, четвёртая попытка — 200. Основное подтверждение email не повторяется для скрытия ошибок.
- Исправлена конфигурация test backup parent: путь должен одинаково существовать на стороне daemon и внутри provisioner; root-owned родитель позволяет штатному helper создавать приватные каталоги UID10001. Это изменение только оператора стенда.
- Фактически завершён attempt5: подтверждение email, создание кабинета настоящим provisioner, password/CSRF/Secure HttpOnly cookie, HTTPS ForwardAuth owner, data-quality, отказ анонимному запросу, authenticated capacity и запрет внешней сети. После перезапуска собственного Docker повторены вход той же личности, роль, HTTPS/data-quality/capacity/egress. Tenant router readiness заняла 2.025 s **после** готовности gateway-маршрута; это не общий RTO сервера. `mechanical-proof-attempt5.json`: все 27 boolean gates=true, own private objects removed, девять посторонних ID/images/mounts сохранены. Attempts1–4 сохранены как отрицательные результаты.
- Benchmark получил read-only frozen SQL fixture, копирование только в новый собственный том, отказ при WAL/SHM/journal, symlink/junction и пересечении путей. Оригинал проверяется по hash; credentials и расписания доставки очищаются только в копии. Unix chmod выполняется до chown, первый mount использует volume-nocopy.
- Полный объём запросов, отчётов и телеметрии обязателен. Исключения потоков, поздний spawn после watchdog, ошибка health, нарушение floor, OOM/restart или оставшиеся ресурсы делают итог отрицательным и возвращают ненулевой exit code. Образ закрепляется immutable ID; source SKU не попадает в публичный proof.

## Реальные ограничения текущего стенда

Windows host: 31.67 GiB RAM, около 14 GiB свободно при preflight; существующая Docker VM: 7.75 GiB / 12 CPU. Она уже содержит девять посторонних сервисов. Hyper-V management в текущем пользовательском токене недоступен; увеличение `.wslconfig` потребовало бы остановки существующей среды. Это не выполнялось.

Поэтому 20–30 не запускались на этой VM. У владельца запрошены отдельный тестовый сервер либо бюджет его временной аренды; ответа пока нет. Целевой geometry для повторяемого прогона — 8 CPU и достаточная RAM с неизменённым admission budget и floor. Сам объём RAM не гарантирует прохождение: отказ на 30 сохраняется как результат.

Первый полноценный прогон должен повторять известную боевую geometry 16 GiB / 8 CPU с теми же caps и admission. По default reservation384 MiB и budget0.7 RAM тридцатый кабинет на 16 GiB может получить штатный отказ; его нельзя обходить. Отдельный вариант 24 GiB / 8 CPU допустим для изучения необходимой ёмкости, но его результат не подтверждает поддержку 30 на существующих 16 GiB. Full-stack DR и density запускаются поочерёдно: восстановленные test tenants не должны незаметно добавляться к объявленным 20/25/30.

Owner-local escrow содержит backup recovery key и ключи пяти существующих кабинетов. Не подтверждены независимый полный deployment env/keyring, TLS/ACME, daemon/NAT, systemd/cron и действующий независимый S3 доступ. Новые синтетические секреты не являются восстановлением утраченных настоящих ключей. Восстановленные сессии SQL автоматически не аннулируются при смене master/bearer — это отдельное действие только на private stand.
