# Общий бюджет запуска кабинетов: выкладка и границы

Ветка `claude/tenant-budget-20261014` от `10266b7`. Закрывает п. 1 из `docs/AUDIT_CAPACITY_VERIFICATION_2026-10-12.md` (глобальный admission budget). Прод не нагружался: все проверки на двойнике Docker и синтетических slug.

## Что делает

Перед созданием/апгрейдом кабинета провизионер проверяет общий бюджет памяти:

- считает **резервы** уже работающих кабинетов (`running`, `restarting`, `paused`) плюс резервы стартов «в полёте», сравнивает с бюджетом хоста;
- проверка и захват резерва делаются под одной блокировкой, поэтому параллельные заявки не могут обе пройти на одну и ту же свободную память;
- не влезло: HTTP 503, `Retry-After: 30`, тело `{"detail": {"code": "capacity_exhausted", "reason": "budget"|"host_memory", "free_mib", "reserved_mib", "budget_mib", "running_tenants", ...}}`. Опционально ждёт до `WB_SAAS_TENANT_ADMISSION_WAIT` секунд (максимум 15), по умолчанию 0;
- резерв освобождается в `finally`, в том числе после ошибки запуска; недозапущенный контейнер (`created`) удаляется, повторная попытка не упирается в конфликт имени;
- **уже работающие кабинеты не останавливаются ни при каком отказе**. Апгрейд работающего кабинета не отказывается и не зависает на полпути: он заменяет сам себя и захватывает резерв без проверки до остановки старого контейнера;
- ожидание стоит вне блокировки жизненного цикла, поэтому `stop`/`remove`, которые освобождают место, не блокируются ожидающим стартом.

Шлюз при 503 `capacity_exhausted` держит регистрацию в статусе `provisioning` (страница `/provisioning` объясняет очередь) и повторяет запуск каждые 20 с до 900 с, потом `failed` с понятным текстом. Повторный вход, пока запуск идёт, второй запуск того же slug не начинает (раньше он мог выполнить `DELETE` чужого запуска).

Новые контейнеры получают `mem_reservation` (мягкий лимит) рядом с прежним жёстким `mem_limit`. Уже работающие контейнеры мягкого лимита не имеют, пока их не пересоздадут; до этого они учитываются по умолчанию (`384m`).

Read-only статус для оператора: `GET /v1/capacity` (под тем же Bearer, что и остальной `/v1/`).

## Настройки (все необязательны)

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `WB_SAAS_TENANT_MEM_RESERVATION` | `384m` | резерв на кабинет; не выше `WB_SAAS_TENANT_MEM_LIMIT` |
| `WB_SAAS_TENANT_MEMORY_BUDGET` | пусто | пусто = доля от RAM хоста; `10g` и т.п.; `off` или `0` = без лимита (аварийный выключатель) |
| `WB_SAAS_TENANT_MEMORY_FRACTION` | `0.7` | доля RAM хоста, если бюджет не задан |
| `WB_SAAS_TENANT_MIN_AVAILABLE` | `1g` | сколько `MemAvailable` хоста должно остаться после старта; `0` = не проверять |
| `WB_SAAS_TENANT_ADMISSION_WAIT` | `0` | сколько секунд старт ждёт в провизионере (≤15, шлюз ждёт 20 с на запрос) |
| `WB_SAAS_PROVISION_CAPACITY_WAIT` | `900` | шлюз: сколько ждать место, секунд |
| `WB_SAAS_PROVISION_CAPACITY_RETRY` | `20` | шлюз: шаг повтора, секунд |

Арифметика для хоста 15 988 MiB (снимок аудита от 12.10): бюджет 0.7 × 15 988 = 11 191 MiB, это 29 кабинетов по 384 MiB; сейчас работают 5 (1 920 MiB). Дополнительно после старта должно остаться ≥ 1 GiB доступной памяти хоста. При 30 кабинетах верхние лимиты (1.5 GiB) в сумме не вмещаются в хост: бюджет ограничивает **приём новых кабинетов по резерву**, а не рост потребления уже работающих.

## Порядок выкладки

1. Смержить ветку. Тесты (из корня worktree):
   ```powershell
   py -3.12 -m pytest provisioner -q                      # 123 passed
   py -3.12 -m pytest gateway/tests -q                    # 596 passed
   ```
2. **Сначала gateway** (новый gateway со старым провизионером работает как раньше: 503 не приходят), затем провизионер. Старый gateway с новым провизионером при нехватке места пометит регистрацию `failed` сразу.
3. До нового провизионера разрешить `INFO=1` только приватному control-proxy. Проверить из старого провизионера, что Docker `info()` возвращает RAM; discovery-proxy оставить без этого доступа. Образ провизионера собирать с `provisioner/Dockerfile` из этой ветки: в `COPY` добавлен `tenant_budget.py`. Пересоздавать через compose (`docker compose up -d --build provisioner`) либо проверенный операторский helper с сохранением сетевого алиаса `provisioner`. Работающие кабинеты это не затрагивает; пока провизионер пересоздаётся, регистрации не стартуют (~секунды).
4. В `.env` новые переменные не обязательны. Рекомендую явно закрепить `WB_SAAS_TENANT_MEM_RESERVATION=384m` и оставить остальные по умолчанию.
5. Проверка после выкладки (только чтение):
   ```bash
   docker exec wb-saas-provisioner-1 python -c "import os,urllib.request as u;r=u.Request('http://127.0.0.1:8001/v1/capacity',headers={'Authorization':'Bearer '+os.environ['WB_SAAS_PROVISIONER_BEARER_KEY']});print(u.urlopen(r).read().decode())"
   ```
   Ожидание: `running_tenants` равно числу работающих кабинетов (сейчас 5), `reserved_mib` ≈ 1920, `budget_mib` ≈ 11191, `would_admit: true`.
6. Откат: образы предыдущих версий; без пересборки бюджет отключается `WB_SAAS_TENANT_MEMORY_BUDGET=off` и `WB_SAAS_TENANT_MIN_AVAILABLE=0` с пересозданием контейнера провизионера.

## Что проверено

На двойнике Docker (без демона, без production-данных):

- 40 параллельных заявок на 12 мест: ровно 12 успешных, 28 отказов 503, ни одного лишнего контейнера;
- волны 20/24/30/36 заявок против бюджета на 20/30 кабинетов: принято ровно `min(заявок, мест)`, ни один работающий не остановлен;
- churn: 30 заявок на 25 мест → 25 принято; остановка трёх освобождает ровно три места, повторы занимают ровно их;
- ошибка запуска освобождает резерв, удаляет недозапущенный контейнер, ждущий старт получает место после `stop`;
- мутационная проверка: тесты падают, если убрать захват резерва, освобождение, принудительный захват апгрейда, очистку после ошибки, определение 503-отказа в шлюзе или защиту от двойного запуска.

## Границы (что это не решает)

- Бюджет считается по резервам, а не по фактическому потреблению. Рост памяти уже работающих кабинетов он не ограничивает; от него защищает только жёсткий `mem_limit` каждого кабинета и проверка `MIN_AVAILABLE` при приёме новых.
- Автоперезапуск Docker после перезагрузки хоста (`restart: unless-stopped`) идёт мимо провизионера и бюджета.
- Обновление демо-кабинета (`/v1/demo/reseed`) заменяет сам себя и проверке бюджета не подвергается.
- Если Docker не отдаёт состояние, RAM хоста неизвестна или включённая проверка `MemAvailable` недоступна, новый старт ждёт: HTTP 503 `capacity_exhausted`, причина `measurement_unavailable`. Чтение `/v1/capacity` также возвращает 503; внутренние ошибки наружу не передаются. Для вычисления доли RAM приватный control-proxy должен разрешать `INFO=1`; discovery-proxy этого разрешения не получает.
- Снимок очереди использует ту же повторно захватываемую блокировку, что и admission, поэтому чтение `/v1/capacity` безопасно при параллельных стартах. Явное `MEMORY_BUDGET=off` отключает только лимит суммы резервов; проверка свободной памяти отключается отдельно через `MIN_AVAILABLE=0`.
- Claim хранится в памяти одного процесса провизионера (один uvicorn-процесс, как сейчас). При нескольких процессах или репликах нужен общий источник правды.
- Реальная нагрузка (одновременная синхронизация и крупные расчёты 20–30 кабинетов), классы лимитов trial/paid и остановка простаивающих кабинетов этой веткой не закрываются.
