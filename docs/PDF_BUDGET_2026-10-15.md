# Общий бюджет памяти фоновых PDF, очередь и долговечные leases

Ветка `claude/pdf-budget-20261019` от `3dc30c3`. Финансовые расчёты, FIFO, права, таймауты запросов и admission не менялись. Деплоя нет.

## Изменения после независимой проверки Codex

Перед общей выкладкой устранены дефекты, найденные на объединённом коде:

- Настроенный общий каталог обязателен: при его недоступности фон остаётся в очереди, синхронный запрос получает `PdfBusy`/503. Скрытой деградации до одного PDF на каждый кабинет больше нет. `status()` отдельно сообщает `configured=true, healthy=false` и не создаёт каталог или lock-файлы.
- Маршрут `/api/v1/operations/reports/pdf` берёт внешний слот с ожиданием до 15 секунд, прежде чем вызывает builder. Внутренний слот реентерабелен.
- Слот удерживается на весь `generate_and_save`: от создания запуска до записи файла и завершения. Heartbeat и завершение сверяют зафиксированные owner и номер попытки; старый обработчик не изменяет новый lease. При старте восстанавливаются истёкшие leases и старые записи без lease, действующий запуск другого процесса не сбрасывается.
- Удаление кабинета разрешает только точно проверенный `/pdf-slots` mount, но не включает общий coordination volume в удаляемые данные. Подменённые, лишние и совпадающие с данными mount-источники отклоняются до удаления.
- Дочерние процессы дополнительных магазинов получают общий бюджет и вычисленный из настоящего `DATA_DIR` замок кабинета; временная snapshot-директория не создаёт отдельную квоту. Вложенная генерация из уже удерживающего слот родителя отклоняется до запуска child. Ручная сборка берёт слот до SQL claim; при занятости возвращается 503 с ограниченным `Retry-After`, исходный snapshot не коммитится. Для этой синхронной child-ветки требуется повтор запроса, а не обещание новой долговечной очереди дополнительных магазинов.

Приведённый ниже benchmark относится к исходной ветке Claude. После исправления startup recovery повторный запуск прерванного задания может ждать истечения lease (по умолчанию 300 секунд). Нельзя переносить прежнее время завершения benchmark на исправленную реализацию без нового замера. OS-lock по-прежнему освобождается при завершении процесса.

## Проблема
Сборка PDF отчёта (pandas + matplotlib) добавляет кабинету 200–340 МиБ на ≈30 секунд и упирается в CPU. Каждый кабинет собирал отчёт, когда хотел, поэтому на одном сервере PDF всех кабинетов могли идти одновременно (на стенде 8 ГиБ несколько одновременных отчётов уводили свободную память ниже порога). Запуск, у которого воркер умер посреди сборки, оставался в `running` до перезапуска воркера, а запуск, убивающий воркер (например по памяти), мог зацикливаться.

## Что сделано
**Слоты на OS-замках** (`tenant-app/reports/pdf_budget.py`). Любая сборка держит слот; если процесс умер (сбой, OOM, остановка контейнера), ядро освобождает слот само, чистить нечего.
- слот кабинета: один PDF одновременно на кабинет между API и воркером;
- слоты сервера: `WB_SAAS_PDF_SLOTS` файлов `pdf-slot-NN.lock` в общем каталоге `WB_SAAS_PDF_SLOT_DIR`, который провизионер монтирует во все кабинеты как `/pdf-slots`. Не настроено: действует только слот кабинета.

**Очередь не ждёт «внутри».** Воркер берёт слот до `claim`: нет места, и запуск остаётся `queued` в базе кабинета (долговечно), следующий тик через 5 с пробует снова, попытка не тратится. Плановый отчёт (`check_once`) остаётся «к выполнению» и не создаёт ошибочный запуск; расписание дня не сгорает. Доставка (почта/Telegram) идёт после освобождения слота. Запросы из интерфейса ждут слот до 15 с, потом `503` с `Retry-After: 30` (`/api/reports/{id}/generate` и `/api/v1/operations/reports/pdf`). `build_report_pdf` сам проходит через слот (другим вызывающим, например теневым воркерам магазинов, достаётся ожидание до `WB_SAAS_PDF_WAIT_SECONDS`, по умолчанию 120 с).

**Долговечные leases** (`tenant-app/reports/store.py`, новые колонки `attempts`, `lease_owner`, `lease_expires_at`, добавляются сами). `claim`/`start_run` выдают lease на 300 с, пока собирается PDF его продлевает heartbeat, `requeue_expired_leases` возвращает запуск в очередь без перезапуска воркера. Запуск, который уже прерывался 3 раза, закрывается понятной ошибкой («возможно, нехватка памяти»), а не зацикливается. При старте воркера восстановление (`requeue_interrupted_runs`) работает как раньше, но с тем же лимитом попыток.

**Провизионер.** `WB_SAAS_PDF_SLOT_HOST_DIR` (абсолютный каталог хоста или имя тома) и `WB_SAAS_PDF_SLOTS` (по умолчанию 2, допустимо 1–32). Кабинеты получают монтирование `/pdf-slots` и переменные; узкий помощник (`chown 10001`, `chmod 770`) готовит каталог; конфигурация проверяется до запуска контейнера. Не задано: спецификация кабинета не меняется ни в чём. **Монтирование входит в контейнер: действует для кабинетов, созданных или обновлённых (`upgrade`) после включения.**

## Включение
1. Задать в `.env` `WB_SAAS_PDF_SLOT_HOST_DIR=/opt/wb-saas/pdf-slots` и `WB_SAAS_PDF_SLOTS=2` (число слотов подбирается по памяти: один слот ≈ 200–340 МиБ и ≈ 1 ядро CPU на ≈30 с), пересоздать провизионер (`docker compose up -d --build provisioner`, алиас сохраняется).
2. Обновлять кабинеты по одному штатным `upgrade`: контейнер получит монтирование и переменные. Без этого шага кабинет остаётся в режиме «только свой слот».
3. Проверка занятости слотов в кабинете: `docker exec <tenant> python3 -c "import sys; sys.path.insert(0,'/app/tenant-app'); from reports import pdf_budget; print(pdf_budget.status())"`.
4. Откат: восстановить исходный образ/Env/mounts каждого обновлённого кабинета и provisioner, затем исходные Compose/pins. Удаление переменных только у provisioner не отключает бюджет в уже работающих кабинетах. Не удалять lock-файлы или общий каталог при активных держателях. При недоступном настроенном каталоге новые сборки остаются заблокированными.

## Измерено (реальные контейнеры, ядро Linux в VM Docker 8 ГиБ, 8 кабинетов, демо-данные)
Скрипт `scripts/bench_pdf_budget.py`, сырые данные `docs/benchmarks/pdf-budget-evidence-2026-10-15.json`. Один запуск отчёта ставится в очередь во всех кабинетах в один момент, собирает штатный резидентный `background_worker`.

| | без бюджета | слоты = 2 |
|---|---:|---:|
| Одновременных PDF (по интервалам запусков) | **8** | **2** (опрос замков: ≤2) |
| Просадка свободной памяти VM, МиБ | **936** (4 759 → 3 823) | **574** (4 625 → 4 051) |
| Время до последнего PDF | 39 с | 117 с |
| Время одного PDF, p50 | 31 с | 27,5 с |
| Пик памяти кабинета, max | 341 МиБ | 334 МиБ |
| `memory.events` high / max / oom / oom_kill | 0 / 0 / 0 / 0 | 0 / 0 / 0 / 0 |
| Throttle CPU, % периодов | 28,0 | 23,8 |
| Запусков ok / ошибок | 8 / 0 | 8 / 0 |

Бюджет не уменьшает память отдельного отчёта (пик кабинета тот же), он ограничивает **одновременность**: цена — время (117 с вместо 39 с при 8 запросах «сразу»), выгода — на 38% меньше просадка памяти хоста и меньше CPU-давление. Чем больше кабинетов в один момент, тем сильнее разница.

**Восстановление после сбоя** (в той же серии, на втором круге очереди): кабинет `t07` убит `SIGKILL` в момент, когда держал слот (занято 2 из 2) и его запуск был `running`. Слот освободился **через 0,2 с**, очередь других кабинетов пошла дальше; после запуска контейнера прерванный запуск был возвращён в очередь и завершился `ok` с `attempts = 2`; последние запуски всех остальных 7 кабинетов `ok`.

## Границы
- Слоты считают сборки, а не байты: «ёмкость в МиБ» задаётся числом слотов (≈ бюджет PDF = слоты × пик одной сборки). Динамического бюджета по фактической свободной памяти нет.
- Межконтейнерные `flock` на общем каталоге надёжны на Linux (bind-монтирование хоста или именованный том). На Docker Desktop с общим доступом к файлам Windows/macOS семантика замков не гарантирована; измерения сделаны на именованном томе в VM Linux.
- Реальная синхронизация с WB и доставка отчётов не проверялись (нет токенов и сети); `sync`/`agents` в демо-данных не работают.
- Измерено 8 кабинетов на стенде 8 ГиБ; 20–30 кабинетов этой веткой не воспроизводились.
- Прерывание `deliver_report` (почта/Telegram) по-прежнему помечается ошибкой доставки без повторной отправки: поведение не менялось.
