# DR на новой ОС: восстановление, host jobs и перезагрузка

16 октября 2026, отдельный локальный Linux-стенд. **Восстановление прикладного контура и настоящая перезагрузка прошли. Полная приёмка сервера DR пока не закрыта.** Production не выкатывался, не перезапускался и не перенастраивался. Во время подготовки ранее сделаны только дополнительные копии и чтение метаданных; новые зашифрованные объекты записаны copy-only и проверены чтением из S3.

## Что подтверждено

- Новая Ubuntu 24.04 из проверенного cloud image, отдельный Docker engine. После публичного bootstrap внешние TCP/UDP/DNS запрещены до передачи приватных данных. Приватный RSA остаётся на Windows. Точные исходные образы проверены по ID.
- Восстановлены 12 сервисов: gateway, provisioner, два Docker proxy, Traefik, пять кабинетов, GlitchTip и PostgreSQL 18. Все настроенные healthcheck зелёные; у двух proxy и Traefik healthcheck не настроен.
- 21 SQLite прошла `integrity_check` после распаковки; PostgreSQL: количества строк во всех 369 таблицах дампа совпали (766 строк), `pg_amcheck` прошёл. Это проверка восстановленного исходного состояния, а не повторный integrity_check всех SQLite после рабочего запуска.
- После reboot: сессии/ForwardAuth/роли для пяти кабинетов, закрытие анонимного доступа к частным кабинетам, реальный bearer provisioner, расшифровка сохранённых WB/Ozon credentials без вызова провайдеров. Вход по паролю не проверялся; используются новые тестовые сессии только на копии, затем они отзываются.
- После reboot: доверенная системная TLS-цепочка и SNI на семи адресах; 32 MP4/VTT по SHA-256/размеру, GET/206/416 и WEBVTT; GlitchTip принял синтетическое событие и сохранил его в PostgreSQL.
- Отдельный Traefik того же исходного образа получил сертификат у приватного Pebble через настоящий HTTP-01 и автоматически обновил его без перезапуска/удаления store. Два различных serial подтверждены. Это тест ACME-механики, не обращение к публичному CA. Проверены shadow DNS и изолированное разрешение рабочих имён; публичная зона не менялась.
- **Настоящий `systemctl reboot`: 346,6 с.** Изменился boot_id; сохранились machine-id, Docker engine, все 12 ID контейнеров и их образов. Контейнеры автоматически запустились, Docker/cron/локальные DNS и SMTP — active/enabled. Cron выполнил новый marker уже после reboot. В конечных `memory.events` контейнеров high/max/oom/oom_kill = 0.

Письма и алерты поступают в локальный SMTP sink; никаких реальных писем/Telegram/платёжных запросов не отправлено. Проверка rclone на стенде не доказывает гостевую аутентификацию в Timeweb S3. Отдельные реальные encrypted copy-only загрузки в S3 и их полный readback зафиксированы в подготовительных квитанциях.

## Что исправлено именно в процедуре репетиции

Первый запуск выявил пропущенные Docker volume labels, сохранённые автоматически созданные hostname, права/наличие каталогов независимого ledger backup и отсутствующий durable статус demo refresh. Получены исходные метаданные, сохранены в отдельный RSA/AES envelope и проверены чтением из S3. На стенде восстановлены labels всех 13 томов; перед их пересозданием содержимое скопировано, хэши и файловые/каталожные uid/gid/mode сверены. Пересозданы только стендовые контейнеры с новыми Docker-generated hostname. Восстановлен настоящий сохранённый статус demo refresh, а не искусственная отметка успеха. CPU/healthcheck deadlines не ослаблялись; попытка отдельной корректировки CPU отказала до изменений и сохранена как отрицательная.

Старые FAIL-квитанции не удалены. Полный linked test с data-quality остаётся FAIL; отдельный access-only PASS его не подменяет.

## Осталось для полной приёмки DR

1. Проверить policy/retention с настоящим S3 в отдельном безопасном контуре. Сейчас отказ `s3_policy_config_unavailable` ожидаем для файлового alias, но успешная приёмка retention не выполнена.
2. Сверить текущие страницы и обновить эталон drift после согласованной проверки. Монитор обнаружил новый `Disallow: /feedback` как critical и 23 отличия от 29 сентября. Эталон молча не перезаписывался.
3. Пройти полный тяжёлый `/api/v1/control/data-quality?period=30d` у mvvorokov: в TCG-стенде запрос превысил таймаут. Это не доказательство такого же отказа production, но и не PASS данной репетиции.
4. Перенести и принять host security/monitoring: исходные UFW/SSH/sysctl сохранены, но на Ubuntu 24.04 не применялись; provider zabbix-agent не восстановлен/не принят. Новая ОС использует отдельный SSH-ключ и внешнюю изоляцию QEMU. Также остаётся публичный DNS/ACME cutover — намеренно не выполнялся без изменения production.

## Границы точки восстановления

Бизнес-данные — из аутентифицированной копии **14 октября**, runtime/config/GlitchTip PostgreSQL — **16 октября**. Глобально атомарная свежая копия всех сервисов на 16 октября не заявляется. Исходная ОС Ubuntu 22.04/Python 3.10, цель Ubuntu 24.04/Python 3.12; host crypto venv собран offline с теми же версиями runtime-зависимостей и проверен реальными backup jobs. Это функциональная TCG-репетиция, не нагрузочная приёмка 20–30 кабинетов и не проверка живой синхронизации маркетплейсов.
