## Изменения после независимой проверки Codex

Перед первым боевым запуском усилена проверка архива: уникальные tar/JSON-имена, ограничения размера/числа членов, независимая проверка approved manifest на все 16 уроков и точное соответствие inventory/metadata/файлов. Проверки поймали дубликаты и неодобренный manifest, принимавшиеся исходным вариантом. Публикация нового cipher исключает перезапись уже существующего файла даже при гонке.

Изолированный gateway запускается с чистым allowlisted окружением и новой SQLite-копией; настройки production Postgres, Sentry, SMTP, Telegram, proxy и erasure не наследуются. Репетиция с боевым ключом не должна подключать production DB или том gateway.

Добавлен `scripts/training_media_backup_job.py`: одна новая проверенная копия в сутки через `pack --force`, затем повторная полная проверка до retention. Источник задаёт `WB_SAAS_TRAINING_MEDIA_SOURCE_DIR`; ключ/KEY_ID/KEYRING существующие, архивы — `<WB_SAAS_BACKUP_DIR>/training-media`. Ошибка даёт стандартный `local_backup_failed` alert без деталей и ключей. Retention удаляет только просроченные аутентифицированные архивы собственного формата с проверенными marker/name/manifest/inode; неизвестные, повреждённые и неподтверждённые чужие копии остаются. Значение keep days по умолчанию 14.

Для cron сначала этот job, затем существующий offsite job. Группа `training-media` должна входить в `WB_SAAS_BACKUP_REQUIRED_GROUPS`. Повторный pack без force пропускает неизменный manifest и не обновляет возраст архива: нельзя использовать это как ежедневную свежую копию или менять mtime для имитации свежести. Факт включения cron/offsite фиксируется отдельно операторским актом, а не этой инструкцией.

Host runner использует проверенный изолированный контейнер и передаёт purpose-key JSON через stdin `docker exec -i`; ключ не добавляется в новую `Config.Env` или аргументы команды. Перед передачей проверяются полный CID, mounts, UID, сеть и лимиты; core dumps отключены. Ежедневный helper получает только пять публичных файлов инструмента/каталога, media read-only и собственную backup-группу read-write. Контейнер и собственная временная metadata удаляются после запуска.

## Что делает инструмент

- **`verify-source`** — все правила gateway плюс полный SHA-256 всех файлов и полнота 16 уроков с субтитрами; все проблемы выводятся списком, а не только первая.
- **`pack`** — copy-only: источник только читается (до и после сравниваются размер и mtime). Пишет **один новый** архив `training-media-<manifest12>-<UTC>-<rand>.tar.gz.enc` в `--backup-dir`, существующее шифрование `WBSAASBK2` (`provisioner/backup_crypto.py`, ключ и `KEY_ID` из `WB_SAAS_BACKUP_ENCRYPTION_KEY[_ID]` как у остальных бэкапов, в вывод не попадает). Ничего не перезаписывает и не удаляет; если архив этого же manifest уже проверяется, ничего не пишет (`already_backed_up`, `--force` создаёт ещё один). Внутри: `BACKUP-INVENTORY.json`, `manifest.json` и 32 файла. После записи архив тут же расшифровывается и сверяется; при сбое удаляется только архив, записанный этим вызовом.
- **`verify-archive`** — расшифровка, проверка аутентичности (GCM), безопасности имён, равенства состава инвентарю, SHA-256 каждого файла и manifest.
- **`restore`** — только в **пустой** каталог (иначе отказ), `O_EXCL`, затем повторная проверка каталога правилами gateway и совпадение с инвентарём; при сбое убираются только созданные файлы. `--read-only` ставит права 0444.
- **`acceptance`** — полная репетиция в изолированном рабочем каталоге (ниже).

## Команды

```bash
# оператору (ключ из окружения, как у других резервных копий)
export WB_SAAS_BACKUP_ENCRYPTION_KEY=...            # и при ротации WB_SAAS_BACKUP_ENCRYPTION_KEY_ID / _KEYRING
python scripts/training_media_backup.py verify-source --source <каталог, смонтированный в /app/training-media>
python scripts/training_media_backup.py pack --source <тот же каталог> --backup-dir <каталог резервных копий>/training-media
python scripts/training_media_backup.py verify-archive --archive <файл .tar.gz.enc>
python scripts/training_media_backup.py restore --archive <файл .tar.gz.enc> --dest <новый пустой каталог> --read-only

# репетиция целиком (временный ключ, ничего не пишет вне --work)
python scripts/training_media_backup.py acceptance --source <каталог> --work <пустой каталог> --out act.json
```

Каталог источника на сервере — host bind, который gateway монтирует как `/app/training-media:ro` (точный путь смотрится в `docker inspect` контейнера gateway; в релизной записи это `/opt/wb-saas/public-media/course-…`). Я его не читал и не менял.

## Что не сделано и границы

- Production и cron не менялись: **включение группы `training-media` в cron, offsite (S3) и учёт свежести резервных копий — отдельное решение выкладки**. Инструмент пишет в любой переданный каталог и совместим по суффиксу `.tar.gz.enc` с существующей ротацией (`_prune_old_backups` применяется только внутри своей группы).
- Реальный ключ production-бэкапов я не использовал; репетиция шла с временным ключом. Первый боевой `pack` и `verify-archive` с настоящим ключом выполняет оператор.
- Изолированный gateway запущен напрямую через uvicorn на localhost; Traefik, TLS и контейнерный `:ro`-mount не воспроизводились (на проде Range 206 и заголовки подтверждены отдельно по живым ответам выше).
- Недоступны для проверки: что лежит на хосте сервера сверх локальной копии (сравнение шло по именам и размерам из публичных ответов, а не по файлам хоста).
- Архив содержит видео без дополнительного сжатия (gzip уровень 1): размер ≈ размеру источника (97 МБ на 99,6 МБ).
