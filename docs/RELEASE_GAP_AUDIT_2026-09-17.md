# Аудит готовности к релизу: чего не хватает (для исполнителя Codex)

Дата: 17.09.2026
Источник: статический просмотр кода и документов репозитория. Приложение и тесты при аудите **не запускались**; каждое утверждение ниже проверяй по указанным файлам перед исправлением.

Связанные документы: `docs/COMMERCIAL_PARITY_AUDIT_2026-09-16.md`, `docs/RELEASE_EVIDENCE_2026-09-17.md`, `docs/TENANT_UI_MIGRATION_2026-09.md`, `docs/superpowers/plans/2026-09-16-commercial-wb-platform.md`.

## Контекст архитектуры

- `gateway/` — FastAPI + Jinja: лендинг, регистрация/логин, биллинг YooKassa, админка, provisioning тенантов.
- `tenant-app/` — доменная логика, SQLite, WB-клиент `wb_api.py`, синхронизация, отчёты; legacy Streamlit UI (`app.py`, `pages/`) заморожен.
- `mh-redesign-lab/` — целевой UI тенанта: React/Vite (`src/App.tsx`, `src/data-source.ts`) + FastAPI-адаптер `tenant-api/api_server.py`. Образ по умолчанию для новых тенантов: `gateway/config.py:22` → `wb-dashboard-tenant:redesign`.
- `frontend/` (Next) — legacy, заморожен.

## Общие ограничения (обязательны для каждой задачи)

- Не выводить WB-токены и ключи Ozon в ответы API, логи, экспорт, JS-бандл. Хранить через существующие `tenant-app/config.py` (`save_token`, `get_token`) и `secure_storage.py`.
- Не дублировать расчёты из `tenant-app` в адаптере или UI.
- Никаких реальных записей в WB (цены, ответы на отзывы, возвраты) в тестах — только моки / изолированная БД.
- Новые функции — только в `mh-redesign-lab`, не в Streamlit и не в `frontend/`.
- На каждую задачу: pytest-тест для API и Vitest-тест для UI; `npm run build` и `npm test` должны проходить.
- Не коммитить секреты, `.tar`, бэкапы, временные папки pytest.

## P0 — блокеры релиза

### P0-1. Подключение WB-токена в новом UI отсутствует

**Статус на audit21: закрыто.** Историческое описание ниже фиксирует исходный разрыв; новый UI и tenant API теперь поддерживают подключение, отключение и повторное чтение карты прав без возврата токена.

**Факт.** Токен можно сохранить только в Streamlit (`tenant-app/pages/settings_page.py:113` → `save_token`) или локальным скриптом `scripts/connect_wb_local.py` / `connect-wb.cmd`. В `mh-redesign-lab/tenant-api/api_server.py` у `PATCH /api/v1/settings` (стр. ~1963) модель `SettingsUpdateInput` принимает только интервалы; `GET /api/v1/settings` отдаёт лишь `wb_connected`/`ozon_connected`. В `src/App.tsx` нет формы ввода токена. Новый тенант на redesign-образе не может подключить магазин.

**Сделать.**
1. `POST /api/v1/settings/wb-token` — принимает токен, проверяет его запросом к WB (например, `WBAPI.test_statistics()` + проверка доступных категорий), сохраняет через `save_token`, возвращает `{connected, scopes: [...], missing_scopes: [...]}` без самого токена.
2. `DELETE /api/v1/settings/wb-token` — отключение.
3. Аналогично для Ozon (`get_ozon_credentials` уже есть — нужна запись).
4. В «Настройках» — блок «Подключения»: поле-пароль, кнопка «Проверить и сохранить», список категорий токена с отметками (Статистика, Аналитика, Продвижение, Цены и скидки, Маркетплейс, Поставки, Отзывы/Вопросы, Возвраты, Финансы, Контент), предупреждение о недостающих.
5. После успешного сохранения — предложить запустить первую синхронизацию (`POST /api/v1/sync`).

**Приёмка.** Токен не появляется ни в одном ответе/логе (тест). Невалидный токен не сохраняется (тест). Свежий тенант без токена проходит путь до первой синхронизации только через новый UI.

### P0-2. Мастер первого запуска (onboarding)

**Факт.** В `src/App.tsx` нет onboarding-сценария; `gateway/templates/provisioning.html` не упоминает WB. Логика онбординга есть только в legacy `tenant-app/onboarding.py`.

**Сделать.** Если `wb_connected=false` или нет ни одной успешной синхронизации — показывать пошаговый экран: (1) подключить токен, (2) глубина истории (`initial_history_days`), (3) запуск и прогресс синхронизации (`/api/v1/sync/status`, `/api/v1/jobs`), (4) заполнить себестоимость (`/api/v1/settings/product-costs`), (5) каналы отчётов (email/Telegram). Шаги можно пропустить, прогресс сохраняется в настройках тенанта.

**Приёмка.** Vitest: пустой тенант видит мастер, подключённый — дашборд. Пустые разделы показывают CTA «Подключите WB», а не нули.

### P0-3. Чеки 54-ФЗ в платежах YooKassa

**Факт.** `gateway/yookassa_client.py` формирует платёж без объекта `receipt`. Продавец — ИП (реквизиты в `gateway/templates/offer.html`).

**Сделать.** Добавить `receipt` (customer.email, items: описание подписки, amount, `vat_code`, `payment_subject: "service"`, `payment_mode: "full_payment"`) для первичного и рекуррентного платежа, параметры — через env в `gateway/config.py` (`WB_SAAS_RECEIPT_ENABLED`, `WB_SAAS_VAT_CODE`, `WB_SAAS_TAX_SYSTEM_CODE`). Если чеки выдаются иначе (настройка магазина ЮKassa/внешняя касса) — задокументировать это в `DEPLOY.md` и оставить флаг выключенным. **Решение о налоговом режиме принимает владелец, не исполнитель.**

**Приёмка.** Тесты `gateway/tests/test_billing.py` проверяют тело запроса с `receipt` при включённом флаге.

### P0-4. Возвраты платежей и история оплат

**Факт.** В `gateway/` нет refund-логики и страницы истории платежей.

**Сделать.** Админ-действие «вернуть платёж» (`gateway/admin_routes.py`, YooKassa Refunds API) с записью в БД и корректировкой `paid_until`; в `/billing` — таблица платежей (дата, сумма, статус, ссылка на чек при наличии).

**Приёмка.** Тесты на webhook `refund.succeeded` и на пересчёт доступа.

### P0-5. Воспроизводимость релиза

**Факт.** В рабочей копии ~100 незакоммиченных файлов (`git status`); в прод ушёл образ, не соответствующий коммиту (признано в `RELEASE_EVIDENCE_2026-09-17.md`).

**Сделать.** Разобрать изменения на логические коммиты, собрать образ из чистого клона, записать в образ label с git SHA, проверить, что `scripts/deploy_verified_tenant.py` отказывается выкладывать образ без SHA.

**Не делать самостоятельно:** push, force-push, удаление веток — только по подтверждению владельца.

## P1 — функционал: backend есть, UI нет или неполный

### P1-1. FBS в разделе «Поставки»

**Факт.** `GET /api/v1/dashboard/supply` (`api_server.py:1864`) возвращает `wb_new_orders` и `acceptance_coefficients`, но `src/data-source.ts` их не адаптирует, а `App.tsx` не показывает. `wb_supplies` урезаются до 12 строк вместе с закупками (`data-source.ts:1085`). Ошибки WB глушатся `except Exception: []` — пользователь не отличит «нет данных» от «нет прав/ошибка».

**Сделать.** Отдельные вкладки: «Новые сборочные задания», «Поставки FBS» (статус, QR через `get_fbs_supply_barcode`), «Коэффициенты приёмки» (склад, дата, коэффициент, фильтр по бесплатной приёмке). Возвращать в API поле `errors: {section: message}` вместо молчаливого пустого списка. Остатки на складах продавца (FBS) — отдельной задачей.

### P1-2. Отзывы, вопросы, возвраты: заменить нативные диалоги

**Факт.** В `App.tsx` 7× `window.prompt`, 10× `window.alert`, 4× `window.confirm`. Отказ по возврату (`processCustomerReturn(..., "reject")`, стр. ~1856) уходит в WB одним кликом без подтверждения — действие необратимо.

**Сделать.** Модальные окна: ответ на отзыв/вопрос (textarea, счётчик символов, шаблоны ответов, предпросмотр), подтверждение для одобрения/отказа возврата с отображением товара и суммы; toast-уведомления вместо `alert`; пагинация (`take/skip`) и фильтр отвеченные/неотвеченные.

**Приёмка.** В `App.tsx` не остаётся `window.prompt/alert` (тест grep в CI или eslint-правило `no-alert`). Vitest: отказ не отправляется без подтверждения.

### P1-3. Пагинация удержаний/штрафов WB

**Факт.** `tenant-app/wb_api.py` `_get_retention_report` — `limit=1000, offset=0`; при >1000 строк пользователю предлагают сократить период (см. `RELEASE_EVIDENCE_2026-09-17.md`).

**Сделать.** Фоновая многостраничная выгрузка по `offset` с учётом лимитов WB, кэш в БД, статус выгрузки в UI.

### P1-4. Цены и скидки — история

Есть загрузка и статус задачи (`/api/v1/products/prices/*`). Добавить экран истории загрузок (список задач, ошибки по товарам) и массовое изменение по выборке с предпросмотром и подтверждением.

### P1-5. Разделы из `COMMERCIAL_PARITY_AUDIT_2026-09-16.md`, не реализованные в новом UI

- Тарифы логистики/хранения, платное хранение, операции при приёмке.
- Воронка продаж и история остатков (Analytics API).
- Чаты с покупателями: API сейчас отдаёт только количество (`get_seller_chats`), нужны список и ответ.
- Управление карточками и медиа (Content API) — можно отложить после релиза.
- Excel-экспорт «Юнит-экономика» и «Сверка» из `tenant-app/report_tools.py` — проверить полноту `GET /api/v1/operations/finance/export` против legacy и добавить недостающие листы.
