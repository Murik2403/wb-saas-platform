Проверен исходный HEAD `91dcab0fd8169f2b8a0fb2c9028501207ca0b1e7`. Это проверка уже внедрённых ограничений и оставшегося общего бюджета сервера. Код и конфигурация production при проверке не изменялись; нагрузочный тест на живом сервере не запускался.

## Что уже исправлено

- В обоих entrypoint один `background_worker.py` заменяет отдельные циклы sync, agents и reports. Он запускает задачи последовательно, использует прежние интервалы и блокировки, восстанавливает прерванные отчёты, изолирует ошибку одной задачи. Импорты тяжёлых бизнес-модулей отложены до запуска соответствующей задачи. Это экономит отдельные интерпретаторы; точная экономия в МБ в этой проверке не измерялась.
- `DashboardResponseCache` ограничен не только числом записей, но и 32 MiB удерживаемых объектов **на экземпляр кэша**. Oversize результат возвращается без сохранения; очистка/expiry/generation race корректно сбрасывают учёт. Это не ограничение всей памяти процесса: временные DataFrame, ответы и фоновые задачи расходуют память отдельно.
- Один `DashboardWorkGuard` сериализует тяжёлые локальные запросы на полный срок расчёта и передачи ответа в одном uvicorn worker. Health/session не ждут этот слот. Выбранный магазин и вложенный ASGI вызов остаются внутри бюджета; отмена активного запроса не выпускает новый расчёт, пока прежний действительно не завершился.
- `get_management_economics` повторно использует scalar memo по совпадающим окнам расходов и освобождает большой исходный snapshot. Старый пункт «пересборка для каждого расхода» в прежнем виде уже не актуален.

Источники: `tenant-app/background_worker.py`, оба `docker-entrypoint.sh`, `mh-redesign-lab/deploy/tenant-staging-entrypoint.sh`, `mh-redesign-lab/tenant-api/dashboard_cache.py`, `dashboard_work_guard.py`, `api_server.py`.

## Что ещё требуется для 20–30 кабинетов

1. **Глобальный admission budget.** Сейчас `provisioner/app.py` использует один `TENANT_MEM_LIMIT`; общего резерва RAM/числа активных контейнеров нет. 20 × 1.5 GiB = 30 GiB, 30 × 1.5 GiB = 45 GiB, ещё без системных сервисов. Сумма верхних лимитов не вмещается в текущий хост. Среднее idle потребление не доказывает безопасность одновременной активности.
2. **Профили нагрузки и наблюдение.** На приватных восстановленных fixtures измерить одновременную синхронизацию, крупные расчёты и выбранные магазины: p50/p95 задержек, пиковую память, memory.events, очередь, CPU и дисковые задержки. Есть безопасный probe `scripts/probe_private_dashboard_memory.py`: он требует network=none, traefik=false, имя release-rehearsal и точный лимит 1.5 GiB. Он проверяет отдельный тенант, не весь сервер.
3. **Жизненный цикл и классы лимитов.** Разные лимиты trial/paid и остановка idle пока отсутствуют. Не понижать лимит trial до 512 MiB и не останавливать пользовательские кабинеты автоматически без расчётных fixtures, корректного запуска при входе и проверки фоновых задач/бэкапов. Это отдельная реализация, не маленькая поправка текущего guard.
4. **Несколько uvicorn workers.** Guard и кэш имеют границу процесса; добавление workers увеличит число одновременно допустимых больших расчётов. Текущий entrypoint запускает один worker. При смене конфигурации нужен общий межпроцессный бюджет или отдельный расчётный worker.

Без этих шагов утверждение «20–30 активных кабинетов выдерживаются на этом сервере» остаётся непроверенным. Уже исправленные background/cache/economics пункты можно закрыть по исходникам и тестам; глобальную ёмкость — оставить отдельным открытым пунктом.

## Дополнительная проверка: обязательные группы резервных копий

На production cron читает `run_backup_cron.py` из релиза `audit-32f67d7`. Его фиксированный список required groups не содержит letoocean и alexdalex-msk; override `WB_SAAS_BACKUP_REQUIRED_GROUPS` отсутствует в cron, `/etc/environment`, `/etc/crontab` и `/opt/wb-saas/.env`. Архивы обоих кабинетов есть и на момент чтения свежее 26 часов. Daily snapshot читает все `tenant_instances`, а offsite copy включает найденную историю: обнаруженный дефект именно в обязательной проверке свежести/отсутствия, не доказанная потеря копий.

План ограниченного исправления (`scripts/run_backup_cron.py`, его профильные тесты):

1. Воспроизвести выпадение нового кабинета из required groups до изменения кода.
2. Получать валидированные slug из текущего реестра через ограниченный по времени read-only docker exec. Сохранять существующий daily контракт SELECT DISTINCT всех tenant_instances: stopped кабинеты остаются, finalized deletion удаляет запись; статус аккаунта не используется для молчаливого исключения данных.
3. Required = control-plane + demo + явно настроенные группы + текущий реестр, без удаления explicit groups. Ошибка реестра/формата должна прекращать job с безопасным кодом и alert, без fallback к старому списку.
4. Проверить отсутствующий архив нового кабинета, сохранение overrides, timeout/provider/invalid-slug failure и отсутствие side effects после отказа. Затем полный scripts suite; выкладку cron из коммита под backup lock выполняет основной агент.

Во время read-only проверки нового inventory getter production вернул **четыре** customer slug: alexdalex-msk, letoocean, marketing, mvvorokov. Публичный demo не записан в customer registry. Поэтому demo сохранён обязательной встроенной группой, а `backup_tenant_volumes._all_slugs()` дополнен demo с dedupe, чтобы ежедневное создание и watchdog покрывали одинаковые пять кабинетов плюс control-plane. Explicit `--only` в ручном script остаётся фильтром; cron запускает полный режим.

Исправление написано с предварительными failing regressions: старый список пропускал новый кабинет; старый daily getter пропускал demo и не обрабатывал отказ реестра безопасным return code. Теперь:

- getter выполняет только SELECT, ограничивает ответ/количество и timeout 30 s, выдаёт только проверенные namespace slug;
- stopped данные остаются обязательными; окончательное удаление строки снимает автоматическое требование новых snapshots, старая encrypted история остаётся в copy-only списке; explicit группы не исчезают;
- отказ/таймаут/некорректный ответ не заменяются пустым реестром или старым списком: job завершает работу с кодом 1 и безопасным alert, snapshot/copy/freshness после отказа не запускаются;
- тесты используют поддельный provider/alert, не делают реальных бэкапов и не отправляют писем.

Профильные тесты после правки: **25 passed** (`gateway/tests/test_backup_tenant_volumes_script.py` + `scripts/tests/test_run_backup_cron.py`). Статус production до отдельной выкладки основным агентом остаётся прежним; локальный код сам по себе cron не обновляет.

Полный `py -3.12 -m pytest scripts/tests -q` после окончательных изменений: **224 passed, 3 skipped**, 20.01 s. Повторное read-only чтение в `2026-10-11T23:18:04Z`: все шесть local groups пока свежее 26 h; demo 83 876 s (последняя копия `2026-10-11T00:00:08Z`), control-plane 22 351 s. До устаревания demo около 2.7 h; следующая суточная задача в 02:15 UTC уже позже порога, поэтому отдельный свежий demo snapshot может потребоваться основному агенту при приёмке. Эта проверка не создавала snapshots и не запускала retention.
