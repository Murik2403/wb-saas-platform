# Планирование потребности в сырье

## Цель

Помочь владельцу магазина увидеть, сколько сырья потребуется для выбранного плана производства, сколько реально нужно докупить и у какого поставщика успеть заказать, при этом создавать внутреннюю заявку только после явного подтверждения.

## Граница продукта

Первый выпуск — планировщик закупки сырья внутри MARKETSHELPER. Он не отправляет заказ поставщику, не обещает автоматическую закупку и не меняет производственный план, остатки, BOM или складские движения. Сначала пользователь получает расчёт, правит его как черновик и отдельным действием создаёт внутреннюю заявку со статусом «Запланировано».

Сценарий:

1. **Предпросмотр (read-only).** Сервер читает спрос/план выпуска, применимую версию BOM, подтверждённые остатки, открытые закупки и справочник поставщиков. Возвращает потребность и объяснение расчёта; запись в БД не выполняет.
2. **Редактирование черновика.** Пользователь меняет количество заказа, поставщика и ожидаемую дату; может распределить неоднозначный план между размерами/вариантами. Черновик остаётся только в клиентском состоянии.
3. **Подтверждение.** Пользователь нажимает «Создать внутреннюю заявку». API заново проверяет исходные данные и все строки, атомарно создаёт одну заявку и запоминает ключ подтверждения. Повтор того же запроса безопасен; тот же ключ с иными правками конфликтует.

## Источник производственной потребности

- Расчёт строится для явно выбранного периода и только из проверяемых величин в единицах готового изделия.
- Приоритетный источник — незакрытые производственные задания tenant-а с положительным плановым количеством и известной датой выпуска. Отменённые и закрытые задания не включаются. Одно задание учитывается один раз по стабильному `task_key`.
- В MVP единственный источник — сохранённые производственные задания. Прогноз продаж WB и рекомендации на основе истории продаж не смешиваются с планом и остаются вне MVP.
- Для продукта без размерных вариантов задача с `chrt_id=0` однозначна. Если у SKU есть варианты и задание/прогноз содержит только `nm_id`, а BOM разных вариантов расходятся, расчёт отмечает объём как `ambiguous_variant_demand`. До расчёта материалов пользователь должен распределить весь такой объём по конкретным вариантам. Не распределённый остаток блокирует подтверждение.
- Если все варианты SKU имеют одинаковый состав, система всё равно не приписывает неизвестный спрос конкретному размеру. Допускается суммировать его по составу только когда нормализованные расход и единицы совпадают у всех доступных вариантов; ответ сохраняет признак `variant_demand_aggregated` и список рассмотренных вариантов.
- Явное распределение пользовательских объёмов не меняет производственные задания; оно действует только внутри конкретного предпросмотра и попадает в его fingerprint.

## BOM и расход

- Для каждой пары `(nm_id, chrt_id)` выбирается последняя сохранённая версия точного BOM (`version DESC`) на момент предпросмотра. В таблице сейчас нет интервалов действия BOM, поэтому план не должен называть версию «действующей на дату» или выбирать её по дате выпуска. Если точного вариантного BOM нет, можно применить последний общий BOM `chrt_id=0` только по существующему правилу релизов, с признаком `fallback_to_base_bom` и видимой меткой «Общий состав».
- План фиксирует `bom_version_id` и расход каждой компоненты из этой версии. Создание новой версии BOM после предпросмотра делает предпросмотр устаревшим.
- Нет BOM, пустой BOM, компонент без имени/единицы, нулевой или некорректный расход — блокирующая причина по соответствующей строке спроса; пропуск таких данных не должен выглядеть как нулевая потребность.
- Потребность каждой компоненты равна сумме `план выпуска × quantity_per_unit` для соответствующих товара, варианта и версии BOM. Совпадающие материалы агрегируются только после проверки единиц измерения.

## Покрытие запаса и закупок

- Остаток сырья берётся только из известного подтверждённого физического остатка (`balance_known=1`) в `material_inventory_color`. Неизвестный баланс имеет состояние «неизвестно» и не считается нулём или доступным покрытием.
- Если физический остаток и действующие FIFO-слои противоречат друг другу, строка помечается как требующая сверки; неподтверждённая разница не уменьшает рекомендацию к закупке.
- Открытая закупка покрывает только позиции `item_type='Сырьё'` в заявках типа «Сырьё» со статусами `Запланировано`, `Заказано`, `Частично оплачено`, `Оплачено`, `В пути` или `Частично получено`. Покрытие позиции — только неполученная часть `max(quantity - posted_quantity, 0)`. Статусы `Отменено` и `Получено` не покрывают будущую потребность; если закрытый заказ оставил неполученное количество, строка получает blocker для сверки. Частичная приёмка учитывается один раз, а не одновременно как остаток заказа и складской приход.
- В покрытие на дату потребности входит ожидаемый остаток заказа только при известной дате поставки не позже даты, когда сырьё нужно производству. Неизвестная или слишком поздняя ETA отображается как риск и не считается гарантированным покрытием.
- Баланс, позиции закупки и BOM сначала переводятся в базовую единицу конкретного материала только через явное известное преобразование. Неизвестное или неоднозначное преобразование единиц блокирует строку; запрещено сопоставлять по одному имени материалы с разными единицами.
- При `tracking_mode=packaged` заказ округляется вверх до рулона по сохранённому `roll_length`; заказная единица — рулон, а нужное количество в базовой единице и излишек после округления показываются отдельно. При `tracking_mode=quantity` используется базовая единица без округления до несуществующей упаковки. В текущей модели нет MOQ поставщика: MVP не придумывает MOQ и не округляет по нему. Любое другое пакетное преобразование допустимо только после явного сохранения коэффициента.

## Поставщик и ETA

- В черновике пользователь выбирает активного поставщика для каждой строки/сгруппированной заявки. Для заполнения ETA разрешено использовать `suppliers.lead_time_days` как предложение, но показывать, что это настройка справочника, а не подтверждение поставщика.
- Если срок поставки отсутствует, дата поставки неизвестна; подтверждение заявки допустимо только с явно введённой пользователем датой. Система не считает её обещанной поставщиком.
- Разные поставщики создают разные внутренние заявки. До подтверждения показываются поставщик, валюта, единицы, количество/упаковки и предполагаемая дата.
- Цены, доставка, налоги или условия оплаты не рассчитываются автоматически, если их нет в подтверждённых данных. Цена может оставаться нулевой/неуказанной только с заметной меткой «Стоимость не заполнена».

## API и состояния

- `POST /api/v1/supply-planning/preview` читает данные и возвращает `preview_fingerprint`, период, строки спроса, использованные версии BOM, материал, потребность, физический остаток, покрытие активными закупками, дефицит, единицу, упаковку, предложенное количество заказа, поставщика/срок, дату потребности, предупреждения и блокирующие причины. Endpoint не создаёт строки или движения.
- `POST /api/v1/supply-planning/confirm` принимает текущий `preview_fingerprint`, UUID `confirmation_key`, выбранные распределения спроса и отредактированные позиции. API заново строит предпросмотр; при несовпадении источников возвращает `409 stale_preview` и требует нового предпросмотра. Неизвестные/неполные/неразрешённые строки нельзя подтвердить.
- API пересчитывает количество, единицы и упаковки на сервере; входящий draft не может подменить `nm_id/chrt_id`, `bom_version_id`, material key или цену, если они не разрешены текущим предпросмотром. Отредактированное количество не может быть меньше рассчитанного дефицита; packaged-строки остаются целым числом рулонов, quantity-строки используют единицу материала.
- В одной транзакции создаются заявка(и), позиции и реестр подтверждений `{confirmation_key, request_hash, preview_fingerprint, order_ids_json}`. Уникальный ключ не допускает двух заявок при повторе. Повтор с тем же ключом и тем же каноническим телом возвращает прежние ID; тот же ключ с изменённым телом возвращает `409 idempotency_conflict` без изменений.
- Preview не резервирует сырьё и не гарантирует его наличие. Два пользователя могут увидеть один остаток; более позднее подтверждение обязано перепроверить данные и вернуть конфликт/обновлённый preview, если покрытие изменилось.
- Все маршруты наследуют tenant-аутентификацию, изоляцию tenant-БД, demo/viewer ограничения и применимые роли. API не инициирует внешний контакт с поставщиком.

## UI

- В существующем React разделе поставок появляется видимый блок «Потребность в сырье» с периодом/источником спроса, объяснением состояния данных и кнопкой предпросмотра.
- Таблица предпросмотра показывает расчёт по каждой строке: спрос и дата потребности, `nm_id/chrt_id`, BOM/version, материал/единица, нужно, доступно физически, ожидается к дате, дефицит, упаковка/округление, поставщик/срок, предупреждения.
- Неоднозначный спрос по размерам имеет форму явного распределения; сумма назначенных вариантов должна равняться исходному объёму. Любой остаток остаётся блокером.
- Редактируемый черновик не пишет на сервер. Кнопка подтверждения недоступна при blocker-строках, неизвестных единицах, неподтверждённом балансе, нулевом/некратном количестве упаковок либо неразрешённом спросе.
- Перед отправкой показано подтверждение количества заявок и позиций. Успех отображает номера внутренних заявок и статус «Запланировано»; сбой/конфликт оставляет черновик и предлагает обновить предпросмотр.
- UI честно отличает «расчётную рекомендацию» и «заявку создана» от «заказано у поставщика».

## Вне MVP

- Автоматическая отправка заказа, писем или сообщений поставщику.
- Прогноз потребности из продаж WB и автоматическое распределение такого прогноза по вариантам.
- Автоматический резерв/списание сырья и автоматическое закрытие производственного задания.
- Предсказание сроков на основе истории поставщика, оптимизация цены/MOQ и cash-flow.
- Автораспределение спроса между размерами по эвристике.
- Автоматическое исправление неизвестного остатка, BOM, единиц или FIFO-расхождений.

## Приёмка

1. Preview пустой/валидный не меняет число заявок, позиций, складских движений, FIFO-слоёв и открытых задач.
2. Версионированный многокомпонентный BOM даёт точные количества, сгруппированные по материалу и единице; вариант использует точную версию или явно отмеченный допустимый общий BOM.
3. Спрос без `chrt_id` при различающихся BOM блокирует расчёт до полного пользовательского распределения; одинаковые составы можно агрегировать только при доказанно одинаковых единицах и расходе.
4. Неизвестный остаток, отсутствующий BOM, несовместимые единицы и расхождение физического остатка с FIFO не маскируются нулём и не позволяют завысить покрытие.
5. Открытая/частично полученная заявка уменьшает дефицит только на остаток позиции и только если ETA подходит; отменённая и полученная не уменьшают его.
6. Упаковка и минимальная партия округляют количество вверх без потери базовой потребности; расчёт отображает округлённый излишек.
7. ETA рассчитывается как явное предложение из срока поставщика, вручную заданная дата видима как пользовательский ввод; неизвестная дата не считается поставкой вовремя. Минимальная партия поставщика не предполагается, поскольку в текущем справочнике такого поля нет.
8. Правка количества/поставщика/ETA меняет только draft; заявка создаётся только подтверждением.
9. Изменение источников, норм/BOM, остатков или открытых закупок после preview возвращает `409 stale_preview`, не создавая заявку.
10. Повтор идентичного подтверждения возвращает те же заявки; тот же UUID с другой правкой возвращает `409` без второй заявки. Несколько поставщиков дают раздельные заявки в одной атомарной операции.
11. Tenant isolation, роли и demo read-only соблюдаются; внешний заказ/контакт никогда не отправляется.
