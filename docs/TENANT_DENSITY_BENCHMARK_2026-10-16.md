# Изолированный benchmark плотности кабинетов — 16.10.2026

Инструмент: `scripts/bench_tenant_density.py`. Сырые данные: `docs/benchmarks/tenant-density-2026-10-16.json`. Прод не нагружался: всё на локальном Docker этого компьютера, с вымышленными данными и внутренней сетью без выхода наружу.

## Что запускалось

- N настоящих контейнеров кабинета с теми же ограничениями, что у провизионера: read-only корень, `cap_drop ALL`, uid 10001, `mem_limit 1536m` (как на проде), `mem_reservation 384m`, 1 CPU, tmpfs как в спецификации; у каждого свой том, засеянный `seed_demo_data.py` (60 дней, вымышленные товары).
- Образ: локальный образ кабинета от 29.09 (слой Python/nginx) с **текущим** кодом `tenant-app` и `tenant-api` и актуальным `tenant-staging-entrypoint.sh` (один `background_worker.py` вместо четырёх циклов). `httpx`/`httpcore` 0.28.1/1.0.9 (версии из `requirements.lock`) скопированы из локального Python. Фронтенд (статика nginx) на память не влияет и не пересобирался.
- Режим демо (`WB_SAAS_IS_DEMO=1`): только чтение, без вызовов маркетплейсов и без токенов.
- Нагрузка: 20 GET-эндпоинтов дашборда (набор из `mobile/scripts/demo-cabinet.json`), 2 прохода, волнами по 5 кабинетов одновременно; первый проход на холодных кэшах.

## Результат (измерено)

Движку Docker на этой машине выдано 8 ГиБ (ваш `.wslconfig`, не менялся), из них около 6 ГиБ было свободно. Скрипт остановил рост, когда прогноз запаса падал ниже 1,5 ГиБ: **на 25 кабинетах он не пошёл**, измерено до 20.

- Простой растёт почти линейно: **≈196 МиБ на каждый добавленный кабинет** (МНК по 5 точкам), с лёгким ростом среднего (173 → 194 МиБ) из-за общей нагрузки на VM. Это совпадает со снимком аудита с сервера (кабинеты 185 МиБ в простое).
- Ответов 5xx и недоступных запросов не было. Из 20 запросов на кабинет за проход 3 стабильно отвечают 4xx демо-данных (409 `customer-quality`: WB не подключён; 422 `management-economics`: нужен параметр). Скрипт после этого прогона разделяет их с настоящими сбоями (`refused_4xx` и `errors`).
- Холодный запрос на кабинет p95 ≈ 250–460 мс, p50 ≈ 6 мс.

## Прогноз (экстраполяция, не измерение)

Линейная модель простоя: 25 кабинетов ≈ 4,8 ГиБ, **30 кабинетов ≈ 5,8 ГиБ**. С нагрузкой (+10–25 МиБ на кабинет в этом наборе) около 6,1–6,5 ГиБ.

Это нижняя оценка, потому что демо-данные малы. Реальные кабинеты тяжелее: по аудиту от 12.10 `mvvorokov` занимает 578 МиБ при тех же лимитах. Ёмкость сервера (15 988 МиБ, на инфраструктуру — gateway, provisioner, Traefik, GlitchTip/PostgreSQL, ОС — закладываю ≈3 ГиБ и держу 1 ГиБ запаса) при средней фактической памяти кабинета M:

| Средняя память кабинета M, МиБ | Сколько кабинетов помещается |
|---:|---:|
| 200 (демо-данные, этот benchmark) | ≈ 59 |
| 300 | ≈ 40 |
| 400 | ≈ 30 |
| 600 (крупный клиент, как mvvorokov) | ≈ 20 |

То есть **30 кабинетов помещаются, если средняя фактическая память не выше ≈400 МиБ**; при тяжёлых клиентах предел ближе к 20. Бюджет запуска (`85e9517`, резерв 384 МиБ, 70% RAM) допустит 29 кабинетов: он согласован с этой оценкой, но остановит приём, а не рост уже работающих.

## Чего benchmark не доказывает

- Размер данных. Демо-набор (≈15 товаров, 60 дней) заметно меньше кабинета с годом продаж: нужен прогон на **восстановленной приватной копии реальных данных**, в этом же скрипте (`--image`, свой набор томов).
- Одновременный пик. Нагрузка шла волнами по 5; один момент «все 30 считают тяжёлый отчёт» не воспроизведён (на VM с 8 ГиБ нельзя безопасно).
- Синхронизация с WB, фоновые отчёты, запись; режим демо их не включает.
- CPU и диск: у VM 12 vCPU и локальный диск, у сервера 8 vCPU; задержки не переносимы на прод.
- Измерено до 20 кабинетов; 25 и 30 получены линейной экстраполяцией. Чтобы измерить 30, нужна VM Docker не меньше ≈10 ГиБ с запасом (поменять `.wslconfig` решаете вы).

## Как повторить

```bash
python scripts/bench_tenant_density.py --image bench-tenant:overlay --steps 1,5,10,15,20,25,30 --out bench.json
```

Скрипт отказывается работать с удалённым движком (`DOCKER_HOST`, контексты с ssh/tcp/prod/staging), трогает только объекты `bench-*` с меткой `wb-saas.benchmark`, делает свои контейнеры первыми кандидатами OOM-killer и всё удаляет по окончании. Образ-оверлей: `FROM <локальный образ кабинета>` и `COPY` текущего `tenant-app/`, `tenant-api/*.py` и entrypoint (при необходимости `pip` зависимости из `requirements.lock`).
