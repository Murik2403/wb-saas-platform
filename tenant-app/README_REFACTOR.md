# WB Dashboard — рефакторинг структуры (шаг 1)

Это результат первого шага: `app.py` (8686 строк) и `db.py` (8408 строк)
разбиты на модули. **Логика внутри функций не менялась** — код физически
перемещён по доменам и досчитаны необходимые импорты между файлами.
Это сделано скриптами (`ast`/`symtable`-анализ), а не вручную, чтобы
исключить опечатки при переносе тысяч строк.

Импорт `from db import X, Y, Z` в остальных файлах (calculations.py, sync.py)

имена, так что снаружи пакет выглядит как прежний единый модуль.

## Как проверено (без реального Streamlit — его нет в среде, где делался рефакторинг)

1. **`db/`** — проверено по-настоящему: пакет импортирован, `init_db()` выполнен,
   вызваны функции из разных доменов, обращающиеся друг к другу (например,
   `wip.py` → `fifo_materials.py`, `procurement.py` → `fifo_materials.py` +
   `fifo_finished_goods.py`). Написан скрипт-валидатор, который прошёлся по всем
   178 функциям/константам и подтвердил, что каждое кросс-модульное имя
   действительно импортировано (без этого будет `NameError` при обращении к
   функции из соседнего модуля).
2. **`app.py` / `pages/` / `ui_helpers.py`** — синтаксис проверен (`py_compile`)
   на каждом файле. Импорты проверены через временную заглушку `streamlit`
   (не настоящий пакет, просто "заглушка"-объект, отвечающая на любой вызов) —
   это подтвердило, что каждый `from db import ...` / `from calculations import ...`
   внутри страниц ссылается на реально существующее имя. Несколько функций
   (`control.render`, `settings_page.render`) вызваны напрямую и отработали
   без ошибок.

## Что нужно сделать вам перед тем, как считать это готовым

Заглушка streamlit не может проверить реальную вёрстку, `st.session_state`,
поведение виджетов и т.д. Обязательно прогоните руками:

```bash
pip install -r requirements.txt
python launcher.py
```

и пройдитесь по всем 10 вкладкам сайдбара — особенно там, где много вложенных
`st.tabs`/`st.session_state` (Производство, Остатки, Закупки — самые большие
страницы). Если что-то поедет — почти наверняка это будет либо опечатка в
одном месте (легко найти по трейсбеку), либо забытая переменная контекста —
в этом случае просто добавьте её в `ctx = {...}` в `app.py` и в соответствующую
строку `ctx["..."] = ctx[...]` в начале `render()` нужной страницы.

## Шаг 2 (продолжение рефакторинга)

Сессия без доступа к PyPI (streamlit/plotly не ставятся — исходящий трафик на
pypi.org в песочнице заблокирован), поэтому реальный Streamlit-прогон
("пройдитесь по всем 10 вкладкам руками") сделать не удалось. Вместо этого
сделано следующее, полностью без сети:

1. **Найден и исправлен реальный баг**: `pages/production.py` не
   компилировался на Python 3.11 (вложенные f-строки с одинаковыми кавычками
   — синтаксис PEP 701, работает только на 3.12+). Строка с
   `kpi_card("Завершение плана", ...)` переписана через промежуточную
   переменную. Весь репозиторий теперь чисто компилируется и на 3.11, и на
   3.12+.
2. **Найден и исправлен реальный баг**: `app.py` содержал полностью
   продублированный блок (строки 85–125 повторяли 127–165) — заголовок
   страницы, выбор периода (`st.segmented_control`/`st.date_input`) и вызов
   `build_dashboard(start, end)` выполнялись дважды подряд без явного `key`.
   В настоящем Streamlit это `StreamlitDuplicateElementId` и падение любой
   страницы, кроме «Настройки»/«Контроль». Дубликат удалён.
3. **Добавлены unit-тесты** (`tests/`, только stdlib `unittest` — работают
   без pytest и без сети): 19 тестов на самую денежную логику —
   `db/fifo_materials.py` (создание/списание/реверс FIFO-слоёв сырья, включая
   порядок FIFO и авто-досоздание слоя из физического остатка),
   интеграция закупка → FIFO-слой → списание в НЗП (`db/procurement.py` →
   `db/wip.py`), и `db/wb_incidents.py` (защитный барьер v6.1, не позволяющий
   списать инцидент ниже текущего контура WB). Каждый тест поднимает
   отдельную временную sqlite-базу через `db.core.init_db()` — реальная
   `data/wb_dashboard.sqlite3` не трогается. Запуск:
   ```bash
   python -m unittest discover -s tests -t .
   ```
   (тот же набор соберётся и через `pytest`, если он у вас есть).
4. **`db/wb_reconciliation.py` (2876 строк) разбит на три подмодуля** ровно
   так, как предлагалось ниже:
   - `db/wb_fifo_reconciliation.py` — сверка FIFO-слоёв с фактом WB, барьер
     готовности (`finished_goods_fifo_guard_status`), прогоны сверки.
   - `db/wb_fbw_evidence.py` — верифицированные поставки FBW как фактическое
     свидетельство прихода (не создаёт слоёв стоимости сама по себе).
   - `db/wb_fifo_reconstruction_v67.py` — ретроактивная реконструкция FIFO
     (`v67`): предпросмотр, применение, откат.
   Разбито скриптом (построчные срезы по AST, без ручного набора текста) и
   проверено: (а) каждая функция/константа перенесена ровно один раз, без
   потерь и дублей — построчная сверка со старым файлом; (б) все
   межмодульные обращения по короткому имени (там, где раньше функции жили
   в одном файле и звали друг друга без импорта) — их оказалось всего 4
   (`wb_fbw_evidence` → `wb_fifo_reconciliation`,
   `wb_fifo_reconstruction_v67` → `wb_fifo_reconciliation` и →
   `wb_fbw_evidence`) — учтены явными `from .… import …`; (в) AST-валидатор
   прошёлся по всем 185 функциям всего пакета `db/` и не нашёл ни одного
   неразрешённого межмодульного имени; (г) все 15 публичных функций из трёх
   новых файлов вызваны напрямую против копии настоящей
   `data/wb_dashboard.sqlite3` и отработали без исключений; (д) весь набор
   unit-тестов из п.3 по-прежнему зелёный после разбиения.
   `db/__init__.py` обновлён на новые пути; снаружи пакета ничего не
   изменилось — `from db import X` работает как раньше.

## Шаг 3 (довести денежную логику до конца тестами)

Закрыт список из «Дальше» выше — добавлено 64 unit-теста (итого 83 в
`tenant-app/`), всё так же чистый stdlib `unittest`, без сети, без
изменений в самой бизнес-логике (только тесты):

1. **`tests/test_fifo_finished_goods.py` (24 теста)** — движок FIFO-слоёв
   готовой продукции: создание слоя, суммирование по локациям (ready/
   inbound/wb) с исключением reversed, авто-досоздание слоя из
   подтверждённого физостатка, порядок списания FIFO (сначала старые
   слои), перемещение между локациями, барьер `COST_PENDING` (нельзя
   продать через слой с неопределённой ретроактивной себестоимостью),
   реверс движения и реверс исходного слоя (с блокировкой, если слой уже
   частично использован), `initialize_finished_goods_fifo` (создание
   opening-слоёв, предупреждение без `reconcile_wb`, списание с
   `reconcile_wb=True`, идемпотентность).
2. **`tests/test_fifo_sales.py` (11 тестов)** — FIFO-себестоimость продаж:
   инициализация трекинга (baseline для уже существующих продаж, чтобы не
   принять 90 дней истории за новые события), списание 1 ед. по FIFO на
   каждую новую продажу, синтетический слой по базовой ставке когда FIFO
   пуст, идемпотентность повторного прогона, восстановление исходной
   себестоимости при возврате по `srid`, поведение при несопоставленном
   возврате, защита от повторного зачёта одного и того же возврата.
3. **`tests/test_wb_fifo_reconciliation.py` (13 тестов)** — сверка FIFO с
   физостатком: главный инвариант v5.9 — расхождения по локации `wb`
   **никогда** не считаются безопасными для автосписания (в отличие от
   `ready`/`inbound`), `apply_finished_goods_reconciliation` создаёт слой
   при избытке, списывает по FIFO при недостаче, пропускает и считает
   `skipped_lines`/`skipped_units` для всех `wb`-расхождений даже в одном
   прогоне с безопасными строками, `fifo_reconciliation_status` отражает
   итоги.
4. **`tests/test_wb_fifo_reconstruction_v67.py` (16 тестов)** — из этого
   огромного (1665 строк) модуля протестированы: (а) `_resolve_reconstruction
   _cost_basis_with_conn` — чистый read-only каскад приоритетов истории
   себестоимости (факт производства → исторический FIFO без синтетических
   слоёв → исторический opening/return → базовая ставка → прогнозная
   ставка → текущий средневзвешенный FIFO → «нет ставки»), включая
   отсечение по дате (`as_of`) и исключение синтетических слоёв как
   исторического свидетельства; (б) защитные барьеры `apply_retroactive_
   fifo_reconstruction_v67`/`rollback_retroactive_fifo_reconstruction_v67`
   — точный текст подтверждения (`APPLY <N>`/`ROLLBACK <run_id>`,
   регистронезависимо) обязателен и проверяется ДО любых побочных
   эффектов, readiness-гейт блокирует Apply на пустой/неготовой базе,
   Rollback отклоняет неизвестный/неприменённый run.
   **Сознательно не протестирован** сам happy path Apply/Rollback (бэкап
   всего sqlite-файла → `BEGIN IMMEDIATE` → replay → commit/restore) — он
   делает `sqlite3.connect()` напрямую по модульной переменной `DB_PATH`,
   импортированной в `wb_fifo_reconstruction_v67.py` отдельно от
   `db.core.DB_PATH` (который подменяют тесты), так что стандартный
   `DbTestCase`-паттерн до него не дотягивается; нужен реальный файл на
   диске и синхронная подмена трёх разных привязок `DB_PATH`
   (`config`/`core`/`wb_fifo_reconstruction_v67`), плюс солидная
   синтетическая история поставок/продаж, чтобы readiness вообще стал
   `True`. Это интеграционный тест для реального хоста, не unit-тест —
   см. `DEPLOY.md` и прогоните Apply/Rollback вручную на тестовых данных
   перед первым использованием на реальном клиенте.

Полный набор (все 4 файла из шага 2 + эти 4): `python -m unittest
discover -s tests -t .` → 83 теста, все зелёные. Реальная
`data/wb_dashboard.sqlite3` проверена по md5 до/после — не тронута.
